# AWS Glossary

**JDBC Driver** — Java Database Connectivity, Java API standard for talking to DBs. Driver = library (jar file) implementing that API for specific DB, translates generic JDBC calls into DB-native wire protocol. Each vendor (Postgres, MySQL, Redshift, Oracle) ships own driver jar. App code stays same regardless of DB (`DriverManager.getConnection(url,user,pass)` → `executeQuery(sql)`), swap driver jar to target different DB, no app logic rewrite. AWS context: Redshift/RDS/Athena all provide downloadable JDBC driver jar to plug into BI tools (Tableau, QuickSight, DBeaver) or Java apps. ODBC = same concept, different API, used by non-Java tools (Excel, Python pyodbc).

**Amazon Athena** — serverless SQL query service over S3 data, engine = Presto. Key point: S3 storage layer itself unstructured (blob store, no schema at storage level), but file *content* often structured (CSV rows, JSON fields, Parquet columns) — Athena defines schema-on-read via external table (DDL or Glue Data Catalog), reads matching S3 files at query time, applies SQL. No data loaded/moved — reads files directly per query, opposite of traditional DB "schema-on-write." Supports CSV/JSON/ORC/Avro/Parquet. Pricing: $5/TB scanned. Common w/ QuickSight for dashboards. Use cases: BI/analytics, query VPC Flow Logs/ELB Logs/CloudTrail trails. Exam tip: "analyze data in S3 using serverless SQL" → Athena.

**Athena Federated Query** — not separate service, feature of Athena. Extends SQL beyond S3 to other sources (DynamoDB, RDS, DocumentDB, CloudWatch Logs, on-prem DBs) via **Data Source Connector** = prebuilt AWS Lambda function per source type, deployed from Serverless App Repo. Query submitted once, Athena parses, routes sub-queries to matching Lambda connector; connector translates generic call → source-native call (DynamoDB API, JDBC, etc), returns data to Athena for federated join/aggregation across sources in single SQL statement. Results optionally written back to S3. Think: plugin system for reaching beyond S3.

**Redshift — OLTP vs OLAP** — Redshift SQL dialect/engine forked from PostgreSQL, familiar syntax, but NOT used as OLTP database. OLTP (Online Transaction Processing) = normal Postgres/MySQL/RDS/Aurora use case, many small transactions, row-based storage, fast single-row insert/update/lookup (app backends). OLAP (Online Analytical Processing) = Redshift's actual job, few large queries scanning millions/billions rows, aggregate/analyze (SUM, GROUP BY, JOIN across huge tables), columnar storage (reads only needed columns, fast for scans, bad for single-row updates). Redshift = data warehouse/BI/analytics/reporting engine, not a drop-in "cloud Postgres" app database despite shared heritage.

**ECS EC2 launch type vs raw Docker on EC2** — Raw Docker on plain EC2 (no ECS): you SSH in, run `docker run` manually or script it, handle scheduling/restart/scaling/LB integration yourself, no central orchestration API. Instance dies → containers gone, no auto-reschedule. ECS EC2 launch type: ECS = orchestrator layer on top. Register EC2 instances into ECS Cluster (ECS agent runs on instance). Define Task Definition (image/CPU/mem/ports) + Service (desired count e.g. "keep 5 running"). ECS scheduler auto-places tasks across cluster, balances load, reschedules onto healthy instances if one dies. Native ALB/NLB integration, CloudWatch, per-task IAM roles, auto-scaling (instance-level ASG + service-level task count). You still manage/patch/scale the EC2 instances themselves — that's the "EC2" part, contrast Fargate where AWS manages instances entirely. Core diff: raw Docker = you are the orchestrator (manual). ECS EC2 = AWS gives orchestration engine, you still own the EC2 instances underneath. "EC2 launch type" naming = reused as adjective for which compute backend ECS uses (EC2 vs Fargate), not a separate new service — same EC2 service, consumed indirectly via ECS.

**ECS Cluster vs Service vs Task** — hierarchy: Cluster → Service → Task → Container. Cluster: logical grouping/namespace, pool of capacity (EC2 or Fargate) where tasks run — just a boundary, no app logic, "where containers live." Service: runs inside a cluster, defines "keep N copies of this Task Definition running always" — desired count, auto-restart on crash, LB target registration, rolling deployments. For long-running always-on apps (web server/API). Task Definition: blueprint — image, CPU/mem, ports, env vars; Service references one to know what to run. Task: actual running instance of that Task Definition (1+ containers running together). Can also run Tasks directly w/o Service (RunTask API) for one-off/batch jobs — no auto-restart/scaling, fire-and-forget; Service = specifically for long-running apps.

**ECS Cluster requirement vs GCP Cloud Run / AWS App Runner** — Cloud Run (GCP): fully serverless, no cluster concept exposed, deploy container directly, Google hides all infra/orchestration. ECS (AWS): cluster = mandatory logical construct always required, even under Fargate. Nuance: ECS+Fargate launch type makes cluster near-invisible/lightweight (just a namespace, no real EC2 to manage, AWS handles compute like Cloud Run does) — conceptually close to Cloud Run but still forces a "create cluster" step first (mostly formality). ECS+EC2 launch type: cluster backed by real EC2 instances you provision/join — heavier than Cloud Run. AWS's actual closest equivalent to Cloud Run (no cluster, pure serverless containers): App Runner — skips ECS/cluster concept entirely, closest 1:1 match to Cloud Run's UX.

**AZ (Availability Zone)** — One or more discrete datacenters, isolated power/network/cooling, inside AWS Region. Region has multiple AZs (usually 3+), connected via low-latency links. Spread resources across AZs to survive single AZ failure (multi-AZ = high availability pattern).

**Region vs AZ naming** — Region = geo area, e.g. `us-east-1`. AZ = specific datacenter inside region, letter suffix, e.g. `us-east-1a`, `us-east-1b`. Region = isolation boundary for compliance/latency (pick near users). AZ = fault-isolation unit for HA within region.

**Rack** — physical server rack in AWS datacenter, set of servers sharing same power supply + network switch. Rack failure (power/switch die) can kill all instances on it. Partition Placement Group spreads partitions across different racks — one rack fails, only that partition's instances affected, other partitions untouched.

**Subnet** — range of IPs (CIDR block) carved out of VPC, tied to single AZ. VPC split into subnets to organize/isolate resources. Public subnet: route to Internet Gateway, instances can get public IP/reach internet. Private subnet: no route to Internet Gateway, no direct internet access (internal/VPN/NAT-gateway-outbound only). Typical: web tier public, DB/app tier private.

**VPC (Virtual Private Cloud)** — logically isolated network in AWS, your own private slice of cloud. Region-scoped, spans all AZs in that region. You define IP range (CIDR), subnets, route tables, gateways, security rules inside it. Contains: subnets (public/private), route tables, Internet Gateway, NAT Gateway, security groups, NACLs. Default VPC exists per region auto; custom VPCs for isolation between environments/apps.

**EBS Volume** — network drive (not physical), attaches to EC2 over network (slight latency vs local disk). Detachable/reattachable across instances quickly. Locked to single AZ — can't attach us-east-1a volume to us-east-1b instance (snapshot it first to move across AZs). Has provisioned capacity: size (GB) + IOPS, set upfront when created, reserved for you. Billed for full provisioned amount regardless of actual usage. Capacity increasable over time (resize). Max size per volume: gp3/io2 Block Express 64 TiB, gp2/io1/st1/sc1 16 TiB — can't hit 1PB on single volume, need RAID-striped multi-volume, EFS, FSx, or S3 for PB-scale.

**TB vs TiB** — TB (Terabyte) = 10^12 bytes, decimal/base 1000. TiB (Tebibyte) = 2^40 bytes, binary/base 1024. 1 TiB ≈ 1.0995 TB (e.g. 64 TiB ≈ 70.4 TB). AWS storage sizing (EBS etc) uses TiB.

**IOPS / PIOPS** — IOPS (Input/Output Operations Per Second): metric for read/write requests disk handles per sec. PIOPS (Provisioned IOPS): you specify exact IOPS upfront when creating volume (io1/io2 type), guaranteed baseline perf — not variable like gp2/gp3 baseline+burst model. Use for workloads needing consistent high perf — databases, critical apps needing >16,000 IOPS. io1 max PIOPS: 64,000 on Nitro instances, 32,000 on others.

**Cluster-aware file system** — filesystem built to handle multiple servers writing to same shared storage simultaneously, coordinates locking so concurrent writes don't corrupt data. Normal filesystems (XFS, EXT4) assume single OS owns disk exclusively, no locking for multi-host concurrent writes → corruption risk. Cluster-aware ones (GFS2, OCFS2) add distributed locking layer. Required for EBS Multi-Attach (io1/io2, up to 16 instances share one volume same AZ).

**KMS / AES-256** — KMS (Key Management Service): AWS service manages encryption keys, create/store/rotate/control access to keys used to encrypt data (EBS, S3, RDS etc). AES-256: encryption algorithm (Advanced Encryption Standard, 256-bit key), symmetric cipher, industry standard, practically unbreakable by brute force. Together: KMS-managed keys used to encrypt data via AES-256 — e.g. EBS volume encryption, KMS holds/manages key, AES-256 does actual data encryption under hood.

**POSIX** — Portable Operating System Interface, standard defining OS behavior: file permissions, ownership, system calls etc. Unix/Linux follow it. EFS is POSIX-compliant filesystem → only mountable on Linux. Windows not POSIX → can't mount EFS, use FSx instead.

**EFS modes** — Performance modes (2): General Purpose (default, low latency, most workloads), Max I/O (higher latency, scales to more throughput/ops, highly parallel workloads/big fleets). Throughput modes (3): Bursting (throughput scales with storage size, burst credits), Provisioned (fixed throughput independent of storage size), Elastic (auto-scales throughput with workload, pay for what used).

**Bursting (EFS)** — short spike above baseline throughput, using saved-up credits. Baseline throughput tied to storage size. Idle time (below-baseline usage) earns credits, banked in credit balance. Workload spike → EFS draws down credits, pushes throughput above baseline temporarily. Credits drain → throughput drops back to baseline till credits reaccumulate. Called "bursting" — temporary spike, not sustained steady-state.

**Cross-Zone Load Balancing** — matters when instance count differs per AZ. Without it: each AZ's LB node only distributes traffic to instances in its own AZ; client traffic still splits evenly across AZ nodes → AZ with fewer instances gets overloaded per-instance (e.g. AZ1 w/ 2 instances gets 25 req/instance, AZ2 w/ 8 instances gets 6.25 req/instance). With it: each node distributes across ALL instances in ALL AZs → total requests spread evenly over total instance count regardless of AZ split (10 req/instance everywhere). Fixes uneven load from unbalanced instance counts across AZs.

**Spot Fleet vs On-Demand pricing** — Spot Fleet: bids on spare EC2 capacity, price floats with supply/demand, up to ~90% cheaper than On-Demand. No upfront cost, no term commitment, pay-as-you-go. AWS can reclaim instance (2min warning) when capacity needed elsewhere — use for fault-tolerant/interruptible workloads (batch, CI, stateless web tiers). On-Demand: fixed hourly/per-second rate, no interruption risk, no commitment — use for unpredictable or short-term workloads needing reliability.

**Spot Fleet composition** — Spot Fleet = set of Spot Instances + optionally On-Demand Instances, launched together to meet target capacity per launch spec. On-Demand portion guarantees baseline capacity when Spot unavailable/reclaimed.

**Network vs Host (IP addressing)** — IP address splits into two parts: network part (identifies which network/subnet, shared by all devices on it) + host part (identifies individual device within that network). Analogy: network = street name, host = house number. CIDR prefix length (/24 etc) = how many leading bits are network part; remaining bits = host part, free to vary per device. Devices sharing same network part can talk directly; different network = need router to bridge. See [[CIDR notation]].

**Private IP ranges (RFC 1918)** — IANA-reserved blocks, never routable on public internet, free for anyone to reuse inside own network(s). Not provider-specific — same 3 ranges apply universally (AWS, GCP, Azure, home routers, on-prem): `10.0.0.0/8` (10.0.0.0–10.255.255.255, ~16.7M addresses, big networks/orgs), `172.16.0.0/12` (172.16.0.0–172.31.255.255, ~1M addresses, AWS default VPC happens to use this range by default — not exclusive to AWS), `192.168.0.0/16` (192.168.0.0–192.168.255.255, ~65K addresses, typical home networks). Any IP outside these 3 ranges = public, must be globally unique, internet-routable. Cloud providers just pick one of these ranges as their default VPC CIDR — you can choose any of the 3 when creating custom VPC. See [[CIDR notation]], [[Private IP]], [[VPC (Virtual Private Cloud)]].

**Private IP** — internal address, VPC-only, used for instance-to-instance comms inside VPC/subnet. Not internet-routable. Stays same on stop/start.

**Public IP** — internet-routable, auto-assigned (optional) on launch if subnet setting enables it. Dynamic — released on stop/terminate, new one on next start. Free.

**Elastic IP (EIP)** — static public IPv4, owned by account till released. Manual allocate/associate, detach/reattach across instances anytime. Survives stop/start. Free while attached to running instance; charged if allocated but unattached or idle.

**Elastic IP vs Public IP** — Public IP: dynamic, tied to instance lifecycle, changes on stop/start, auto-assigned. Elastic IP: static, tied to account not instance, survives stop/start, movable across instances, manual management.

**Proprietary vs open-source (DB context)** — Proprietary: owned/built by one company, closed internals, locked to that vendor (e.g. Aurora, DynamoDB, Redshift — AWS-built, can't self-host elsewhere). Open-source: code public, portable, can run on-prem or other cloud (MySQL, PostgreSQL, MariaDB). Trade-off: proprietary = better native perf/integration, harder migrate away (vendor lock-in). Open-source = portable, easier exit, often cheaper.

**RDS vs Aurora** — RDS = managed service umbrella (AWS handles provisioning/patching/backup/failover), not itself a DB engine. You pick engine to run inside RDS: open-source (MySQL, PostgreSQL, MariaDB), commercial non-AWS (Oracle, SQL Server), or AWS-proprietary (**Aurora**, MySQL/PostgreSQL-compatible). Aurora IS an RDS engine option, not separate from RDS. Aurora diffs from standard RDS engines: proprietary storage layer, decoupled compute/storage, auto-scale storage to 128TB, faster (~5x MySQL/3x PostgreSQL claim), 6-way replication across 3 AZ automatic, faster failover (~30s), costlier. Standard RDS engine: EBS-backed manual storage provisioning, cheaper, portable off AWS. Exam angle: choose Aurora for AWS-native perf/scale/HA, standard engine for portability/cost/on-prem compat.

**ALB listener rule conditions** — rules match requests to route to target groups. Mutually exclusive (pick one per rule): `host-header`, `http-request-method`, `path-pattern`, `source-ip` (CIDR-based). Combinable, can add alongside: `http-header`, `query-string`. Up to 3 comparison strings per condition, 5 per rule. Confirms ALB CAN route by source IP natively. Source: docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-rules.html

**Aurora Global Database — RTO on promote** — Global Database = 1 primary region (read/write) + up to 10 secondary regions (read-only), replication lag <1s. Disaster recovery: if primary region dies, "promote" a secondary region → flips it from read-only to read/write, becomes new primary. That promotion completes in <1 min (RTO = Recovery Time Objective, i.e. downtime duration). Apps redirect writes to newly-promoted region after switch. Contrast w/ plain Aurora Cross-Region Read Replicas — simpler DR option, no defined RTO guarantee like Global Database.

**ElastiCache — Redis vs Memcached** — Redis: Multi-AZ w/ auto-failover, read replicas (scale reads + HA), data durability via AOF persistence, backup/restore, supports Sets/Sorted Sets. Single-threaded, replication R→R. Also: rich data structures (strings/lists/sets/sorted sets/hashes/streams), Pub/Sub messaging, transactions, clustering (sharding) for scale. Memcached: multi-node partitioning (sharding) not replication, no HA/no replication, non-persistent (data lost on restart), backup/restore only in Serverless mode, multi-threaded architecture (better multi-core CPU use per node), simple key-value only (strings/objects), simpler/less overhead. Exam angle: need persistence/replication/HA/complex data structures/pub-sub → Redis. Need simple, fast, multi-threaded, horizontally-sharded cache, no durability required → Memcached.

**AOF (Append Only File) persistence — Redis** — Redis logs every write operation to a file as it happens. Crash/restart → Redis replays log, rebuilds dataset from scratch. Gives durability — data survives reboot. Contrast Memcached: pure in-memory, no persistence, data lost on restart.

**Auto-failover (RDS/Aurora) + Multi-AZ vs Cross-Region Replicas vs Global Database** — Auto-failover: primary DB instance dies (crash/AZ outage/patching) → AWS auto-promotes standby/replica to primary, no manual action, apps reconnect via same DNS endpoint. RDS Multi-AZ: standby copy in different AZ, sync replication, standby not normally readable, auto-failover ~1-2min. Aurora Multi-AZ: 6-way replication across 3 AZs built into storage layer, any read replica can auto-promote, faster failover ~30s. Both = HA within one region only.
Scaling out to cross-region DR: Aurora Cross-Region Read Replicas = simple manual DR option, no auto-failover, no defined RTO — promote manually if region dies. Aurora Global Database = built for cross-region DR at scale: 1 primary region + up to 10 secondary regions, replication lag <1s, up to 16 read replicas per secondary region, promote secondary → RTO <1min (still manual trigger, but fast/managed), also cuts read latency for global users (secondary regions serve local reads). See [[Aurora Global Database — RTO on promote]].

**Authoritative vs Non-authoritative DNS** — Authoritative: server hold actual zone record, source of truth for domain (e.g. Route 53 for domain it host). Answer direct, no cache, response has "AA" (Authoritative Answer) flag set. Domain owner control/publish records here. Non-authoritative: resolver (ISP resolver, 8.8.8.8, etc) answer from cache, not original source. Faster response, but record maybe stale till TTL expire. No AA flag in response. Check via `dig <domain>` — look at flags line, `aa` present = authoritative answer. See [[DNS name vs IP address]].

**Route 53 Health Checks — Threshold + Global Checkers** — Healthy/Unhealthy Threshold (default 3): flip status only after 3 consecutive checks same result (fail 3x straight → mark unhealthy, pass 3x straight → mark healthy). Avoids flapping on single blip. Interval: 30 sec default (10 sec = "fast" interval, higher cost). Global checkers: ~15 checker nodes spread across AWS regions worldwide, each independently polls endpoint from own region. Overall endpoint status = majority vote across checkers (need min 3 of 15 report healthy by default, %-based threshold, configurable if fewer regions selected). Purpose: avoid one region's network blip flagging global outage — distributed consensus, not single point of check.

**Route 53 Health Checks — String Match** — not just HTTP status code check. Can configure "search string" — checker scans first 5120 bytes of response body for specific text. Found → healthy. Not found → unhealthy, even if status 200 OK. Use case: endpoint returns 200 but body says "Database Error" — string match catches it, pure status-code check misses it.

**CIDR notation** — compact notation for IP range, format `IP/prefix-length` (e.g. `10.0.0.0/16`). Prefix = # leading bits fixed (network portion), rest = host range. 32 total bits (IPv4), fewer fixed bits = more free bits = bigger range (2^free-bits addresses). Smaller /number = wider range, bigger /number = narrower range. Common: `/32` = 1 exact IP, `/24` = 256 IPs (typical subnet), `/16` = 65,536 IPs (typical VPC), `0.0.0.0/0` = all IPv4 addresses (whole internet, wildcard). Firewall context (Security Groups/NACLs): source/destination fields take CIDR not just single IP. `0.0.0.0/0` inbound = allow from anywhere (public web ports). Home IP `/32` = allow only that exact IP (tight, e.g. SSH restricted to you). `10.0.0.0/16` = allow from anywhere inside that VPC (internal-only, no internet exposure).

**CNAME record** — maps hostname → another hostname (not directly to IP). `app.example.com CNAME → target.example.com`, resolver then looks up target's own record (A/AAAA/another CNAME) — indirect, extra hop. Contrast: A = name→IPv4 direct, AAAA = name→IPv6 direct, CNAME = name→another name. Rule: CNAME can't coexist with other record types on same name.

**Zone apex + CNAME restriction + Alias record** — Zone apex = root of domain, no subdomain prefix (e.g. `example.com`, not `www.example.com`). CNAME record illegal at zone apex: apex node must hold SOA (Start of Authority) + NS (Name Server) records, mandatory for zone to function. CNAME rule says name with CNAME can hold no other record type → conflicts with apex's mandatory SOA+NS → so CNAME banned at apex by DNS spec. Practical: `www.example.com CNAME → target` fine (subdomain), `example.com CNAME → target` illegal (naked domain/apex). AWS fix: Route53 **Alias record** — behaves like CNAME (points to AWS resource name not IP) but implemented as extension of A/AAAA record type, legal at apex, coexists with SOA/NS. Free, no extra lookup charge, use for pointing apex domain at ALB/CloudFront/S3 etc.

**Route 53 — IP-Based Routing Policy** — you define mapping: CIDR block → endpoint. Query comes in, Route53 checks requester's source IP, matches against your CIDR list, returns endpoint tied to matching block. No match → falls to default record. Why CIDRs relate to ISPs: ISPs get allocated big contiguous CIDR block(s) from RIR (ARIN/RIPE/APNIC etc), hand out IPs to customers from that block (usually dynamic DHCP) — so any IP inside block ⇒ traffic from that ISP, regardless which exact customer. Big ISPs often fragment into many scattered CIDR blocks over time (mergers, regional acquisitions), not one neat range — public whois/RIR registries track current owner per block. Use case: known network-path issue for ISP-X users (bad peering/latency) → map ISP-X's CIDR range(s) → optimized endpoint, bypass bad path. Difference vs Geolocation policy: Geolocation = geographic location of resolver (coarse, country/continent). IP-based = exact CIDR ranges you define — precise control down to specific network blocks/ISPs, not geography per se. See [[CIDR notation]].

**NS record vs CNAME record** — different purpose, not comparable roles. NS (Name Server): says which DNS servers are authoritative for a zone/domain, e.g. `example.com NS → ns1.aws.com, ns2.aws.com`. Tells resolvers "ask THESE servers for anything under this zone" — delegation, not individual name→address mapping. Required at zone apex, every domain must have NS records (delegation chain root→TLD→your zone). CNAME: alias one hostname to another hostname, `app.example.com CNAME → target.example.com`. Resolves a specific name to another name (eventually down to IP). Can't exist at zone apex, can't coexist w/ other records on same name. Optional, case-by-case subdomain aliasing. Analogy: NS = "office handling all mail for this building." CNAME = "room 4B mail redirects to room 7C." See [[CNAME record]], [[Zone apex + CNAME restriction + Alias record]].

**DNS name vs IP address** — IP: numeric location, machine-routable (e.g. `54.239.28.85`), L3 concept, what routers actually use. DNS name: human-readable label (e.g. `www.example.com`), not routable itself, resolved to IP via DNS lookup before connection made. DNS decouples identity (name) from location (IP) — underlying IP can change (failover, scaling) without changing the name clients use. AWS: ALB/NLB expose DNS name not fixed IP, since backing IPs shift as AWS scales nodes — don't hardcode LB IP. Route 53 = AWS DNS service. Record types: A (name→IPv4), AAAA (name→IPv6), CNAME (name→another name), Alias (AWS-specific, name→AWS resource, works at zone apex where CNAME can't).

**EBS (Elastic Block Store)** — persistent block storage, network-attached to EC2 (like virtual hard drive). Survives instance stop/terminate unless delete-on-termination flag set. Snapshot to S3 possible. Types: gp3/gp2 (SSD, general purpose), io1/io2 (high IOPS, latency-sensitive DB), st1/sc1 (HDD, throughput/cold, big sequential workloads).

**Golden AMI vs User Data (bootstrapping)** — Bootstrapping = process of instance self-configuring on first boot. Golden AMI: the disk image itself — pre-baked snapshot w/ software/configs/patches, built ahead of time, boots FROM it. Fast/consistent launch, but stale till rebaked. User Data: script that runs AFTER instance boots (cloud-init style), executes live at launch time — installs packages, pulls secrets, registers w/ LB, sets hostname. Flexible/dynamic, but slower boot + runtime dependency risk (network, external services). Not the same layer — AMI = which image you boot from, user data = what runs after boot. Common combo: golden AMI for base stack + user data for instance-specific final config.

**Stateless (AWS context)** — instance/service holds no persistent session data locally, any request can hit any instance w/ same result. Contrast stateful: server remembers client (session in instance memory/local disk), needs sticky sessions to route client back to same instance. State instead lives externally: session data → ElastiCache/DynamoDB, files → S3, DB state → RDS/Aurora. Why matters: stateless instances freely replaceable — safe for ASG scale-in/out, Spot interruption, no broken sessions on termination. See [[EBS]].

**EBS — cross-AZ attach** — EBS volume locked to its AZ, cannot attach directly to instance in different AZ. Workaround: create snapshot (snapshot is region-wide, not AZ-bound) → create new volume from snapshot in target AZ → attach to instance there. Data effectively "moves," underlying volume itself does not.

**Golden AMI vs EFS — fixing slow per-deploy dependency resolution** — Problem pattern: Elastic Beanstalk (or any EC2 deploy) resolves dependencies (npm install/pip install/etc) fresh on EVERY instance on EVERY deploy → slow. Fix = Golden AMI, not EFS. Why EFS wrong: storing dep files on EFS doesn't skip the resolution step — instance still runs install/resolve logic at deploy time, just reading from network storage (maybe slower, network I/O). Root cause untouched. Why Golden AMI right: deps resolved ONCE at AMI-build time, baked into image. Deploy time = instance just boots from pre-baked image, zero resolution step, no repeated work. Key distinction: not "managed vs unmanaged service," it's "bake once ahead of time vs resolve every single deploy." See [[Golden AMI vs User Data (bootstrapping)]].

**S3 Security — 4 mechanisms + ACL scopes** — User-based: IAM Policies (which API calls allowed for specific IAM user). Resource-based: Bucket Policies (bucket-wide rules, allows cross-account), Object ACL (per-object grant, fine grain, can be disabled), Bucket ACL (bucket-wide grant, legacy/less common, can be disabled). All 4 distinct, not overlapping duplicates. IAM principal can access S3 object if (user IAM policy ALLOWS OR resource policy ALLOWS) AND no explicit DENY. Note: AWS now recommends disabling ACLs entirely (default for new buckets since 2023 — "Bucket owner enforced"), use Bucket Policy + IAM instead; ACLs kept for legacy/backward-compat cross-account cases.

**Fine grain vs coarse grain (access control)** — Fine grain = precise/granular control, smaller unit of scope — e.g. S3 Object ACL, permission set per individual file, differs file to file. Coarse grain = broad/blanket control, bigger unit of scope — e.g. S3 Bucket Policy/ACL, one rule applies to everything inside. Analogy: coarse = lock on building door (same access for everyone inside), fine = lock on each room (different key per room). See [[S3 Security — 4 mechanisms + ACL scopes]].

**IAM Role vs Policy** — Policy = document defining permissions (JSON, what actions allowed/denied on which resources). Rules only, does nothing alone, must attach to identity. Role = assumable identity (no password/access keys), used by trusted entity (EC2, Lambda, cross-account, federated user). Policies attach TO role (or user/group) — role = "who," policy = "what allowed." Key diff vs IAM User: User = permanent identity, long-term credentials. Role = temporary identity, no fixed credentials, assumed on-demand via STS, auto-expiring temp tokens. Analogy: Policy = job description, Role = temp badge worn to get those permissions, User = permanent employee badge.

**IAM Group vs Role** — Group = collection of IAM Users, not an identity itself, can't be assumed/logged into. Just a container to attach policies to many users at once (bulk permission management). No credentials of its own, permissions inherited by member Users. Role = standalone assumable identity, own temp credentials via STS when assumed, usable by humans (cross-account/federated) or AWS services (EC2, Lambda). Can't put Role inside Group, can't assume a Group. Different category: Group = organizational grouping of Users, Role = identity you temporarily become. See [[IAM Role vs Policy]].

**CloudTrail — auditing KMS key usage** — CloudTrail logs every KMS API call (Encrypt, Decrypt, GenerateDataKey etc): who (IAM user/role), which key, when, source IP, success/fail. S3 SSE-KMS: each object upload/download triggers key use → logged. Enables: see who accessed encrypted data + when, spot unauthorized/unusual decrypt attempts, prove compliance for audits, detect key compromise/misuse. KMS = does encryption, CloudTrail = audit trail of every key op. See [[KMS / AES-256]].

**ACL (FSx for Windows context)** — Access Control List, Windows NTFS-style permission set on files/folders (same model as Windows File Explorer → Properties → Security tab). Per-user/per-group rules: read/write/execute, granted per file or folder. FSx for Windows integrates with Active Directory, so ACLs tie directly to AD users/groups (e.g. Finance group = R/W on \\share\finance, Sales group = read-only). Distinct from S3 ACL (bucket/object-level grant, see [[S3 Security — 4 mechanisms + ACL scopes]]) — same acronym, different layer/protocol.

**FSx vs S3** — FSx: managed file system, mount via OS (drive letter/mount point), normal file I/O (open/read/write/seek), protocol-based (SMB for FSx Windows, POSIX/Lustre for FSx Lustre). Supports file locking, concurrent edits, real directory hierarchy, POSIX permissions. Low-latency, high IOPS — good for lift-shift legacy apps expecting filesystem access, HPC/ML scratch space. Pricier (provisioned capacity/throughput). S3: object store, HTTP/REST API only (GET/PUT), no true directory hierarchy (key prefixes look like folders), no file locking, no in-place edit (overwrite = atomic replace, no rename — copy+delete). Higher per-request latency but scales infinite, cheap, pay-per-use. Rule of thumb: app expects `C:\shared\file.txt`-style access → FSx. App fine calling API to store/fetch blobs → S3. See [[POSIX]].

**FSx for NetApp ONTAP** — NetApp = third-party storage company, ONTAP = their storage OS, run on-prem for decades (dedup, compression, snapshots, SnapMirror replication). AWS partnered w/ NetApp, offers ONTAP as managed FSx service — enterprises already running NetApp on-prem migrate to cloud w/o rewriting storage layer/tooling. Multi-protocol: NFS + SMB + iSCSI simultaneous access to same data (Linux + Windows clients both hit same files). Storage tiering (hot SSD, auto-tier cold to cheaper capacity pool), sub-ms latency. vs other FSx flavors: FSx Windows = SMB only, AD-integrated. FSx Lustre = POSIX, HPC/ML scratch. FSx ONTAP = only one doing NFS+SMB+iSCSI natively same data. Real trigger = protocol breadth, not "Linux + cheap" (OpenZFS also Linux/cheap — overlaps). ONTAP wins when: multi-protocol stated (NFS+SMB/iSCSI same dataset), migrating FROM on-prem NetApp (SnapMirror/CLI compat), need iSCSI block storage, enterprise-grade dedup. See [[FSx vs S3]], [[FSx for OpenZFS]].

**FSx for OpenZFS** — managed version of ZFS filesystem (open-source, originally Sun Microsystems). ZFS known for: snapshots + clones (instant, cheap, copy-on-write), data integrity checksumming (catches silent corruption), built-in compression, high IOPS/low latency. FSx OpenZFS specifics: NFS protocol only (Linux/Unix clients), sub-ms latency, cheap/fast snapshots+clones (great for spinning up dev/test copies of prod data fast), generally cheapest FSx option, good price/perf for Linux NFS workloads. Full FSx lineup: Windows = SMB, AD-integrated, Windows-native. Lustre = POSIX, HPC/ML high-throughput scratch. ONTAP = NFS+SMB+iSCSI multi-protocol, NetApp shops migrating on-prem tooling. OpenZFS = NFS only, Linux-native, cheap snapshots/clones, general-purpose. Exam trigger: "Linux workload, need cheap/fast snapshots, NFS" → OpenZFS. See [[FSx for NetApp ONTAP]], [[FSx vs S3]].

**FSx for OpenZFS** — managed version of ZFS filesystem (open-source, orig Sun Microsystems). Known for: snapshots/clones (instant, cheap, copy-on-write), data integrity checksumming (catches silent corruption), built-in compression, high IOPS/low latency. FSx flavor specifics: NFS only (Linux/Unix clients, no SMB), sub-ms latency, cheap/fast clones — good for spinning up dev/test copies of prod data instantly. Generally cheapest FSx option for Linux NFS workloads. OpenZFS vs ONTAP wins when: pure Linux/NFS only (no Windows/SMB/iSCSI need), cost matters most, fast/cheap instant clones needed, no NetApp legacy migration angle. Real differentiator vs ONTAP isn't "Linux vs not" or "cheap vs not" (both true for either) — it's protocol breadth (ONTAP multi-protocol) vs pure-Linux simplicity+clone speed (OpenZFS). See [[FSx for NetApp ONTAP]].

**FSx overview — all 4 flavors compared** — FSx Windows File Server: SMB, Windows-native, AD-integrated (NTFS ACLs tied to AD users/groups), lift-shift Windows file shares. FSx Lustre: POSIX/Lustre client, Linux, HPC/ML high-throughput parallel compute, S3 data-lake integration, massive scale IOPS/throughput. FSx NetApp ONTAP: NFS+SMB+iSCSI multi-protocol same dataset, enterprise NetApp migration (SnapMirror/CLI compat), dedup built-in. FSx OpenZFS: NFS only, Linux, cheapest option, fast/cheap instant snapshots+clones (great dev/test), compression but no real dedup. Quick pick: Windows/SMB/AD shop → Windows File Server. HPC/ML parallel compute → Lustre. Need multi-protocol or migrating real NetApp gear → ONTAP. Pure Linux + cost + fast clones → OpenZFS. Overlap trap: ONTAP and OpenZFS both do Linux/NFS and both "cheap-ish" — real differentiator is protocol breadth (ONTAP) vs pure-Linux simplicity/clone-speed/lowest-cost (OpenZFS), not "Linux vs not." See [[FSx for NetApp ONTAP]], [[FSx for OpenZFS]], [[FSx vs S3]], [[POSIX]].

**S3 = proprietary, unlike EFS/NFS** — "Proprietary" = owned/controlled by one company, closed interface, locked to that vendor (opposite of open-source/open-standard). NFS (Network File System) = open standard protocol, any OS/vendor implements it, works same everywhere. EFS = AWS managed service but built ON TOP of NFS protocol — standards-compliant, mountable like normal Linux filesystem, POSIX-compliant (see [[POSIX]]). S3 = no standard protocol underneath, AWS-invented interface, access only via S3's own REST API (GET/PUT, SDK calls) — no POSIX, no NFS, no mount-and-go. Code written for S3 API only works w/ S3 (or S3-compatible shim elsewhere), not portable to generic filesystem mount — unlike EFS/NFS which follow portable industry standard.

**NFS vs SMB** — both = file-sharing protocols, remote clients access files over network as if local. NFS (Network File System): open standard, orig Sun Microsystems, Linux/Unix native. Client mounts remote share, works like local folder — open/read/write/seek same as local disk. Used by EFS, FSx OpenZFS/Lustre/ONTAP. SMB (Server Message Block, formerly CIFS): Microsoft protocol, Windows native, mount remote share as drive letter (`\\server\share`), file/print sharing. Used by FSx Windows File Server, FSx ONTAP. Key diff: NFS = Linux world, SMB = Windows world, different wire protocols, not interchangeable — client OS needs matching protocol support. Why FSx offers multiple flavors — Windows uses SMB, Lustre/OpenZFS use NFS, ONTAP does both. See [[FSx overview — all 4 flavors compared]], [[POSIX]].

**FSx ONTAP — "High OS Compatibility"** — official AWS slide phrase for ONTAP's multi-protocol support (NFS+SMB+iSCSI). Means Linux boxes (NFS), Windows boxes (SMB), block-storage-needing apps (iSCSI) all connect to SAME ONTAP filesystem simultaneously, no OS left out. Contrast FSx Windows (SMB/Windows only) or FSx Lustre/OpenZFS (NFS/Linux only) — those lock to one OS family. ONTAP = broadest compatibility across mixed-OS environments. See [[FSx for NetApp ONTAP]], [[NFS vs SMB]].

**AWS DataSync vs Transfer Family** — different job, easy to confuse (both move files). DataSync: migration/sync tool, point at source (on-prem NFS/SMB/HDFS, S3 API, other cloud) + destination (S3/EFS/FSx), copies data over, scheduled or one-time. Needs agent for on-prem source (see [[AWS DataSync — agent meaning]] if saved). Use case: bulk migrate/replicate large datasets, own infra to own infra. Transfer Family: managed file-transfer server, hosts SFTP/FTPS/FTP(S) endpoints backed by S3/EFS. External users/partners connect w/ standard FTP client, upload/download like normal FTP server — actually S3 under hood. Use case: give third parties standard file-transfer access to your bucket (supplier uploads invoices via SFTP). Core distinction: DataSync = you migrating/syncing YOUR data between storage systems (push, scheduled, bulk). Transfer Family = you exposing S3/EFS as SFTP/FTP endpoint for OTHERS to connect to (server model, ongoing user access). Exam trigger: "migrate/sync on-prem to S3" → DataSync. "Partners need SFTP access to our bucket" → Transfer Family. Also covers AWS-to-AWS: DataSync migrates between two AWS storage services too (e.g. S3→EFS), no agent needed for that case (agent only required when on-prem source involved) — "sync your own data between storage systems" holds whether source is on-prem or already AWS. Transfer Family stays wrong for AWS-to-AWS moves since no external party is involved.

**S3 Replication — no chaining** — Bucket1→Bucket2 replication rule + Bucket2→Bucket3 replication rule does NOT cascade: object created in B1 replicates to B2, but does not go on to B3. Why: replication rule fires only on objects PUT DIRECTLY (by user/app) into the bucket — object arriving via replication (from another bucket) is not treated as a "new direct-PUT" event, so downstream rule doesn't trigger for it. Object dead-ends at B2. Reason AWS built it this way: avoid infinite loop risk (e.g. accidental B1→B2→B1 cycle) and unpredictable runaway fan-out across chained buckets — each replication rule = one explicit hop only, no implicit cascading. Other replication notes: only NEW objects replicate after enabling (use S3 Batch Replication for existing/failed objects); delete markers replicate only if opted in; deletes WITH version ID never replicate (prevents malicious delete propagation).

**SQS Visibility Timeout — duplicate processing mechanism** — t=0: ConsumerA polls → gets msg → 30s (default) visibility clock starts, msg hidden from others during window. ConsumerA never deletes msg (crashed, processing >30s, forgot DeleteMessage call) → window expires → msg visible again → next poll returns same msg to ConsumerB (or retry) → processed twice, since ConsumerA may have half-done work already. Fixes: ChangeMessageVisibility API — consumer mid-processing calls this to extend timeout ("still working"), prevents premature release. Tune timeout ≈ actual processing time: too high + crash → stuck msg, reprocessing delayed hours. Too low → timeout expires before genuinely-slow-but-still-working consumer finishes → false-positive reprocessing → duplicates. See [[SQS — same message consumed by 2 consumers?]].

**SQS — same message consumed by 2 consumers?** — Normally no, by design (competing consumers model). Msg pulled by ConsumerA → invisible to others for visibility timeout period (default 30s) → ConsumerA processes+deletes → gone for good. Only exception: ConsumerA doesn't delete in time (crash/slow) → timeout expires → msg reappears → ConsumerB picks it up → possible both process it (duplicate risk, why consumers should be idempotent). Standard queue (not FIFO) also has at-least-once guarantee only — rare duplicate delivery possible even w/o timeout issue. Not simultaneous delivery — sequential: 2nd consumer only gets msg after 1st's window expires unconsumed. Want deliberate multi-consumer fanout (each gets own full copy)? Wrong tool — use SNS→SQS fanout instead, each queue independent.

**SQS "no need to provision throughput"** — SQS scales auto, no config needed, no shard concept. Contrast Kinesis: pick # shards upfront, each shard = fixed capacity (1MB/s in, 2MB/s out) — that's "provisioning throughput," manual/planned ahead. SQS: send/receive as much as needed, AWS handles scaling behind scenes, add more consumers → just works, no throughput limit to plan around.

**Kinesis replay** — consumer can re-read old records, not just newest ones — data stays in stream for retention window (24h default, up to 365d), doesn't vanish after 1 read. Contrast SQS: msg read → deleted → gone, no re-read. Kinesis: reading doesn't delete data, each consumer tracks own position (sequence number/checkpoint) independently. Why useful: consumer crashes/bug → fix code → replay from earlier point → reprocess correctly, no data loss. New consumer added later → can start from beginning of retention window, sees historical records too, not just future. Multiple consumers at different positions simultaneously, each moves at own pace. Example: stream holds 24h clickstream. Bug found in processing logic → fix → rerun from timestamp X → reprocesses same source records w/ fixed logic.

**Real-time data → S3/Redshift + transform = Firehose signature** — Exam pattern: keywords "large amount real-time data" + "load into S3/Redshift" + "transformed before delivery" → answer = Kinesis Data Streams + Kinesis Data Firehose. Why: KDS ingests real-time stream (producer→KDS), Firehose reads from KDS as source, Firehose has native direct-delivery integration to S3/Redshift/OpenSearch/Splunk, Firehose supports inline Lambda transform step before writing to destination — one managed pipeline covers all 3 requirements. Wrong answers to recognize: SQS+Lambda — SQS has no native S3/Redshift connector, requires custom glue code, not purpose-built. SNS+HTTP Endpoint — pub/sub + generic webhook, no built-in S3/Redshift delivery or transform step, wrong tool for structured data pipeline. See [[Kinesis Data Streams vs Firehose]].

**Kinesis Shards** — shard = throughput unit inside a stream. Stream = logical container, capacity actually divided into shards, each shard fixed capacity: In 1MB/s write + 1000 records/s write, Out 2MB/s read. "6 shards provisioned" = told AWS upfront give 6 units → total stream capacity = 6MB/s in / 6000 rec/s in / 12MB/s out. "Provisioned" = fixed upfront, manual scaling (add/remove shards = resharding), doesn't grow itself — contrast On-Demand mode which auto-scales capacity. Shards also = parallelism unit: record routed to specific shard via partition key hash, more shards = more parallel throughput, but consumers need ~1 processor per shard to read in parallel. `ProvisionedThroughputExceeded` exception → exceeded in/out capacity of current shard count → fix = add more shards, covers both example: stream w/ 6 shards (6MB/s in, 12MB/s out), traffic spikes 2x to 10MB/s in / 16MB/s out → exceeds both → need ≥10 shards (covers 10MB/s in, in also covers 16MB/s out since 10 shards×2MB/s=20MB/s out capacity).

**Kinesis Data Streams vs Firehose** — KDS: real-time, custom consumers (KCL/SDK) write code to read/process records. You manage shards (throughput = # shards). Data retained 24h default (up to 365d), replayable. Multiple independent consumers can read same stream. Latency ~200ms. Use: custom real-time processing, need replay/multiple readers. Firehose: fully managed delivery service, no consumer code — point at destination (S3, Redshift, OpenSearch, Splunk, HTTP endpoint). No shard mgmt, auto-scales. Near real-time (buffers by size/time e.g. 60s/1MB before delivery, ~60s min latency). No storage/replay — passes through, not retained. Optional Lambda transform + format conversion (JSON→Parquet) before delivery. Use: load streaming data into data lake/warehouse, zero-ops, no custom processing needed. Often chained: KDS→Firehose→S3 (KDS for real-time processing, Firehose for durable delivery to storage).

**SQS/SNS Deduplication** — drops duplicate messages so consumer processes once, not twice. Only FIFO queues/topics dedup (Standard doesn't). Why duplicates happen: not intentional — producer calls SendMessage, SQS receives+stores it fine, but ack response lost on way back (network blip/timeout) → producer thinks send failed → retries → same msg sent again → 2 copies land in queue. Also: app crashes after sending but before marking "done" locally → restart re-sends same event. Mechanism: Dedup ID (explicit `MessageDeduplicationId` or auto content-based SHA-256 hash of body) + 5-min dedup window — 2nd msg w/ same dedup ID within 5 min silently dropped, not enqueued again. SNS FIFO topic: same idea, dedups at publish time before fanning out to subscribers. Guards against network-retry duplicates, not against sender deliberately publishing 2 different logical messages.

**S3 Events to multiple SQS queues** — S3 event notif config: only 1 rule allowed per (event type, prefix) combo, e.g. one rule for (ObjectCreated, `images/`). Each rule targets exactly 1 destination (1 queue OR 1 topic OR 1 lambda) — can't attach 2 queues directly to same rule. Fix: point rule at SNS topic instead of queue, subscribe multiple SQS queues to that topic (SNS fanout). Example: bucket `my-photos-bucket`, event `ObjectCreated:*`, prefix `images/` → target SNS topic `image-uploads-topic` → topic has 2 subscribers, QueueA (order-processing) + QueueB (thumbnail-gen). Upload `images/pic1.jpg` → S3 fires event → SNS → both queues get copy of message.

**S3 Storage Class Durability/Availability (Standard, Standard-IA, Intelligent-Tiering vs One Zone-IA)** — S3 Standard, Standard-IA, Intelligent-Tiering: data auto-replicated across minimum 3 AZs in region, always on, no config/toggle needed. Withstand loss of 2 whole AZs concurrently, no data loss. 11 nines durability. S3 Standard availability 99.99%, Standard-IA 99.9%. This is a baked-in storage-class property, distinct from Cross-Region Replication (CRR) which is a separate opt-in feature for cross-region copies. S3 One Zone-IA: single AZ only, ~20% cheaper than Standard-IA, 99.5% availability — if that AZ destroyed, data lost. Common confusion: people misremember "AZ destroyed = data lost" as applying to all IA classes, but it only applies to One Zone-IA (name says it). Also easy to conflate with EBS, which is single-AZ by default unless manually snapshotted/replicated.

**S3 Standard vs Glacier Instant Retrieval** — Both: millisecond retrieval, multi-AZ (3+), 11 nines durability. Differ: Standard = frequent access, higher storage cost, no retrieval fee, no min storage duration, 99.99% availability. Glacier Instant Retrieval = rare access (~1x/quarter), ~68% cheaper storage, per-GB retrieval fee, 90-day min storage duration (early delete fee), 99.9% availability. Use Glacier IR when data rarely touched but needs instant access when touched (medical images, media archives).

**Glacier Flexible Retrieval tiers (Expedited/Standard/Bulk)** — Glacier Flexible Retrieval (formerly "Glacier") has 3 retrieval speed tiers: Expedited (1-5 min, most expensive, best-effort unless provisioned capacity purchased for guaranteed speed during high demand), Standard (3-5 hours, normal cost), Bulk (5-12 hours, cheapest, for large datasets). Turkish for "expedited": "Hızlandırılmış" (sped up/accelerated).

**DMS vs DataSync** — both AWS migration/sync services, different data type. DMS (Database Migration Service): moves database records, source→target DB (on-prem or AWS, homogeneous or heterogeneous e.g. Oracle→Aurora via Schema Conversion Tool), one-time bulk load + optional ongoing CDC (Change Data Capture, replicates new inserts/updates/deletes continuously, near-real-time). Row/table-level. DataSync: moves files/objects, source→destination storage (NFS/SMB/HDFS/S3 on-prem or cloud → S3/EFS/FSx), scheduled or one-time sync, file-level copy not DB-aware, no schema/transaction concept. Rule of thumb: structured DB data + need ongoing replication → DMS. Files/filesystem data → DataSync. See [[AWS DataSync vs Transfer Family]].

**S3 Glacier Vault Lock / WORM** — WORM = Write Once Read Many. Vault Lock: attach a lock policy to a Glacier vault; once locked, policy becomes immutable — cannot edit or delete, not even by root. Used for regulatory compliance (finance, healthcare, legal) to prove data is untampered and unerasable for a retention period (e.g. "no delete for 7 years"). Lock process: draft policy → 24hr testing/abort window → permanent lock.

**JWT (JSON Web Token)** — encoded stateless auth token. Structure: `header.payload.signature`. Payload = base64-encoded claims (user ID, email, permissions, expiry) — readable but not secret. Signature = cryptographic hash proving token not tampered. Stateless: no server session storage, each server verifies signature to trust token. Scalable across servers, portable between systems. Payload not encrypted — don't store secrets in it. Includes expiry (exp claim) — after expiry, invalid.

**DynamoDB Transactions** — multi-operation guarantee: all succeed together or all rollback, no partial updates. TransactWriteItems (multiple writes), TransactGetItems (consistent snapshot reads). Prevents data corruption in complex flows (e.g. debit account + credit account both succeed, or both fail). Uses ACID properties: Atomic (all-or-nothing), Consistent (valid state only), Isolated (concurrent ops don't interfere), Durable (once committed, survives crashes).

**DynamoDB Scalar Types** — primitive single-value data types: String, Number, Binary, Boolean, Null. Contrast Document Types (List, Map) = nested structures, Set Types (String Set, Number Set, Binary Set) = collections of scalars.

**CloudFront + Lambda@Edge relationship** — CloudFront = global CDN, Lambda@Edge = serverless compute at edge locations. Lambda@Edge intercepts 4 points in request/response flow: Viewer Request (from client) → Origin Request (to origin) → Origin Response (from origin) → Viewer Response (to client). Enables dynamic logic at edge without origin round-trip.

**Lambda@Edge / CloudFront Functions SEO use cases** — Server-Side Rendering for crawlers (detect bot, pre-render HTML w/ meta tags), dynamic meta/og/canonical tag injection, URL normalization (prevent duplicates), geo-specific content + hreflang, different sitemap/robots.txt per region, bot traffic filtering before origin.

**Bot Mitigation at Edge** — malicious bots scrape, brute-force, DDoS, click-fraud, inventory hoard. Detect+block at CloudFront before reaching origin: JS execution checks, rate-limit, CAPTCHA challenge, allow good bots (Googlebot/Bingbot). Protects origin bandwidth/CPU/DB load.

**Lambda Free Tier — GB-seconds** — 400,000 GB-seconds/month. GB-seconds = memory (GB) × execution time (seconds). Example: 1GB memory × 10 seconds = 10 GB-seconds. 256MB (0.25GB) memory × 40 seconds = 10 GB-seconds. Track both # requests (free tier: 1M) and compute time against limits.

**DynamoDB Streams vs MongoDB Change Streams** — DynamoDB Streams: capture inserts/updates/deletes, auto-trigger Lambda functions, 24h retention. MongoDB Change Streams: equivalent feature, captures same events, app listener model (pull, not push), configurable retention. Both real-time data pipeline use: sync to cache, index, audit logs, microservice events.

**Cognito Identity Pools — auth sources** — Exchange token from ANY source (Cognito User Pools, Google, Facebook, SAML, OpenID, unauthenticated guest) for temporary AWS credentials. User Pools = NOT required; Identity Pools = authorization layer flexible on "who are you" — doesn't care auth source, just validates token + issues credentials to access S3/DynamoDB/etc.

**API Gateway — caching layer** — API Gateway has own response cache, separate/stacked from any backend cache (e.g. DAX for DynamoDB). Per-stage, TTL 0-3600s (default 300s), key by chosen request params, sized 0.5GB-237GB, extra cost. Caches API responses so repeat requests skip Lambda invoke entirely — cuts calls to compute layer, not just DB layer. Two independent cache layers possible in one stack: API Gateway (response cache, client-facing) + DAX (DynamoDB query cache, data-layer).

**OAC (Origin Access Control)** — CloudFront→S3 security mechanism. Problem: S3 bucket behind CloudFront but bucket itself public → anyone bypasses CloudFront, hits S3 URL directly, skips caching/WAF/signed-URLs/geo-restrictions. Fix: S3 bucket policy locked private (block all public access), only specific CloudFront distribution (via OAC identity) allowed GET, requests SigV4-signed by CloudFront to origin. Forces "CloudFront only" access path. Replaces older OAI (Origin Access Identity) — OAI legacy/weaker (no SSE-KMS support, not all regions), OAC = current recommended, supports SSE-KMS buckets + all regions + all S3 actions.

**Lambda default networking — no VPC, no security group** — Lambda w/o explicit VPC config runs in AWS-managed network, reaches other AWS services (SQS, DynamoDB etc) via public AWS endpoints — no security group concept applies at all. Security groups only exist once Lambda explicitly attached to a VPC (needed e.g. to reach private RDS in private subnet) — that attachment forces picking subnets + SG, which then controls outbound from Lambda's ENI. Exam trap: symptom "Lambda reads fine, one specific write action fails" (e.g. can read DynamoDB Stream but can't SendMessage to SQS) → root cause = IAM execution role missing that action's permission, NOT security group/networking — especially when VPC never mentioned in scenario (default = no VPC = no SG to blame).

**Site-to-Site VPN vs Direct Connect vs VPN CloudHub** — three ways connect on-prem to AWS. Site-to-Site VPN: encrypted IPsec tunnel over public internet, customer gateway (CGW) ↔ virtual gateway (VGW/TGW), fast setup (minutes), cheap, ~1.25Gbps/tunnel cap, variable latency (internet path). Direct Connect (DX): dedicated private physical fiber link, on-prem to AWS colo, no internet involved, consistent low latency, high bandwidth (50Mbps-100Gbps), pricier, weeks-months provision. Not encrypted by default — layer VPN on top (DX+VPN) for encryption. VPN CloudHub: hub-and-spoke using multiple Site-to-Site VPN connections terminating on one VGW — lets multiple on-prem sites talk to EACH OTHER through AWS (not just site-to-AWS), cheap alternative to full mesh when no DX available, still internet-based/bandwidth-limited. See [[IPsec]], [[ECMP — scaling VPN bandwidth via Transit Gateway]].

**IPsec** — Internet Protocol Security, protocol suite encrypting+authenticating IP packets. Two main pieces: IKE (Internet Key Exchange) — negotiates/sets up secure tunnel, exchanges keys. ESP (Encapsulating Security Payload) — actual encrypt+auth of packet data. Modes: Tunnel mode (whole IP packet encrypted, wrapped in new packet — used by site-to-site VPN), Transport mode (only payload encrypted, header stays — less common here). AWS Site-to-Site VPN = 2 IPsec tunnels (redundancy) between CGW and VGW/TGW, each own public IP, for failover. See [[Site-to-Site VPN vs Direct Connect vs VPN CloudHub]].

**ECMP — scaling VPN bandwidth via Transit Gateway** — ECMP (Equal Cost Multi-Path) = routing strategy forwarding packets over multiple equal-cost best paths instead of picking one. Problem: single Site-to-Site VPN tunnel capped ~1.25Gbps, protocol limit, can't just make tunnel bigger. Fix: create multiple VPN connections (each = 2 tunnels) from CGW to Transit Gateway (TGW), advertise same route via BGP on all of them → TGW sees multiple equal-cost paths → ECMP spreads traffic across all tunnels, per-flow hash. Result: N tunnels × ~1.25Gbps ≈ aggregate bandwidth scales with N (4 VPN connections ≈ 5Gbps). Catch: single TCP flow still pinned to one tunnel by hash — per-flow bandwidth capped at 1.25Gbps, only aggregate (many parallel flows) scales. Regular VGW (non-transit) does NOT support ECMP this way — reason TGW is preferred architecture for scaling VPN bandwidth. See [[Site-to-Site VPN vs Direct Connect vs VPN CloudHub]].

**OLTP (Online Transaction Processing)** — workload type: lots of small fast transactions (insert/update/delete/read single rows), strong consistency, ACID, normalized relational schema w/ joins. Example: e-commerce order placed, bank transfer, signup. Contrast OLAP (Online Analytical Processing): big aggregation/reporting queries over huge datasets, denormalized (Redshift/data warehouse). RDS/Aurora = OLTP fit (relational + joins + transactional integrity).

**Amazon Keyspaces** — managed serverless Apache Cassandra-compatible service (CQL). Name derived from Cassandra term "keyspace" = top-level container for tables (like "database"/"schema" in SQL world), defines replication strategy, holds multiple tables. Use: migrate existing Cassandra workloads to AWS without managing servers. Part of NoSQL lineup alongside DynamoDB (~JSON), ElastiCache (key/value), Neptune (graphs), DocumentDB (MongoDB-compat).

**ElastiCache Redis — Sharding** — cluster mode splits dataset across up to 500 shards, each shard = 1 primary + up to 5 read replicas, data partitioned by hash slot. Scales both storage AND write throughput (each shard handles own key subset), not just reads. Contrast plain Multi-AZ read replicas: full copy of same data per replica, scales reads only, no write scaling.

**S3 Resource ARN — bucket vs object level**  — `arn:aws:s3:::bucket-name` = bucket-level resource, only valid for bucket-level actions (`s3:ListBucket`, `s3:GetBucketPolicy`, `s3:GetBucketLocation`). `arn:aws:s3:::bucket-name/*` = object-level resource (every object inside bucket), required for object-level actions (`s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`). Mismatch trap: bucket policy grants `s3:GetObject` but Resource = bucket ARN without `/*` → action/resource type mismatch → AWS finds no matching allow → implicit deny → user still can't read files, even though policy "looks" correct and syntactically valid. Fix: append `/*` to resource for any object-level action. See [[S3 Security — 4 mechanisms + ACL scopes]].

**EC2 must be in VPC** — EC2 instances always run inside a VPC (either default VPC auto-created, or custom VPC you specify). Cannot exist outside VPC. Can configure internet access: Internet Gateway attached to VPC + Public Subnet routing + EC2 public IP/Elastic IP + Security Group inbound rules (e.g. allow port 80/443 from 0.0.0.0/0). Private EC2: in private subnet (no internet gateway route), no public IP.

**Columnar storage format (ORC/Parquet) vs row-based (CSV)** — "columnar" = physical byte layout on disk, not logical schema. CSV has column *structure* (delimiter-separated fields) but row-oriented *physical layout*: bytes stored record-by-record, e.g. `1,Alice,30\n2,Bob,25\n` — id/name/age interleaved every line. Reading just one column still means scanning every byte of every row. True columnar formats (ORC = Optimized Row Columnar, from Hive/Hadoop; Parquet, from Spark ecosystem) physically rearrange bytes so all values of one column sit together as a contiguous block: `[1,2,3][Alice,Bob,Carol][30,25,40]`. Query needing one column jumps straight to that block, skips rest entirely — way less I/O. Same-type values packed together also compress far better than mixed-type rows. Why it matters for [[Amazon Athena]]/Redshift Spectrum: analytics workloads scan few columns across many rows (OLAP pattern) — columnar format reads a fraction of total data, directly cuts $/TB-scanned cost. Tradeoff: bad for "fetch full record by id" (OLTP pattern) since one row's fields are scattered across separate column blocks, must reassemble.

**AWS Lake Formation — Blueprint** — workflow template, not a data-origin tag/label. Pick blueprint type (Database, Log file, etc), point at source (RDS table, S3 path) → Lake Formation auto-generates + runs a Glue workflow: crawler discovers schema, ETL job extracts data, loads into S3 data lake, registers in Glue Data Catalog. Function = automate the repeatable "get data from source X into lake" setup, replacing manual Glue job authoring — recipe for the ingestion workflow, not a tracking label on the data itself.

**CloudWatch — standard metric vs custom metric** — Standard metrics (CPUUtilization, NetworkIn, DiskReadOps): visible to hypervisor from outside the guest OS, AWS host collects/sends automatically, no agent needed. Custom metrics (RAM usage, disk space used, running processes, in-OS logs): live INSIDE the guest OS, hypervisor can't see inside OS memory/processes — requires CloudWatch Agent installed in instance, agent pushes metric to CloudWatch manually. Rule of thumb: if metric measurable from outside VM (host/hardware level) → standard. If only visible from inside OS → custom, needs agent.

**EC2 Instance Recovery** — auto-recovery action triggered by CloudWatch Alarm on `StatusCheckFailed_System` metric (system status check = underlying hardware, not instance status check = guest OS). Flow: EC2 instance → CloudWatch monitors it → alarm fires on system check fail → triggers Instance Recovery action → instance stopped and restarted on new healthy host. "Recovery: Same Private, Public, Elastic IP, metadata, placement group" = what gets preserved across the move — instance reborn on new hardware but keeps same identity, so nothing downstream (DNS, configs, other services referencing its IP) breaks. Only fires on system status check failure (hardware problem); instance status check failure (OS-level) needs manual reboot/fix, no auto-recovery for that.

**Jitter vs Latency** — Latency = single measurement, how long one request/probe takes (e.g. 50ms). Jitter = variation/spread across many latency measurements over time (e.g. 50ms, 52ms, 90ms, 48ms → jitter = that swing). Not same thing: can have high latency + low jitter (slow but steady, e.g. always 200ms — fine for normal web load), or low latency + high jitter (usually fast, randomly spikes — bad for real-time). CloudWatch Synthetics/Network Monitor context: repeated probes measure RTT each time, jitter = fluctuation between consecutive probes. Matters most for VoIP/video/real-time — inconsistent delay causes buffering/glitches even if avg latency fine.

**CloudTrail vs CloudWatch** — different job. CloudTrail = audit log, records WHO did WHAT — every API call across account (console/CLI/SDK): caller, timestamp, source IP, resource, success/fail. Answers "who deleted this bucket at 3am." Governance/compliance/forensics, not real-time monitoring. CloudWatch = monitoring/observability — metrics (CPU%, request count, latency), logs (app/system via agent), alarms (trigger action on threshold breach), events/EventBridge (react to state changes). Answers "is system healthy now / alert me if not." Simple split: CloudTrail = API activity history (accountability), CloudWatch = performance/health data (operations). Overlap: CloudTrail logs can feed CloudWatch Logs + trigger CloudWatch Alarms (e.g. alert on root login) — integration point, not same service.

**Sid (Statement ID)** — optional identifier field inside IAM policy `Statement` block. Labels/references statement, no effect on permission logic itself. Must be unique within statement array if used. Optional in IAM policies, required in some contexts (e.g. S3 bucket policies for cross-account access). Example:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3Read",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "*"
    }
  ]
}
```

**Tagging** — key-value label attached to AWS resource, e.g. `CostCenter: 100`, `Environment: prod`. Up to 50 tags/resource, set at creation or after (console/CLI/API/CloudFormation). Uses: cost tracking (Cost Explorer group/filter spend by tag), organization (find/filter resources by attribute), automation (scripts target resources by tag), access control (ABAC — IAM policy condition checks resource tag), compliance/governance (enforce required tags via Tag Policies — see [[AWS Organizations — Tag Policies]]).

**AWS Organizations — Tag Policies** — Org-level governance feature, standardizes tags across accounts in an AWS Organization (not IAM/permissions layer, separate governance layer). Define allowed tag key (exact casing) + allowed values org-wide via JSON policy. Structure: `tags.<key>.tag_key.@@assign` = enforced exact key casing (e.g. `"CostCenter"` — rejects `costCenter`/`COST_CENTER`), `tag_value.@@assign` = allowed value list (e.g. `["100","200"]`), `enforced_for.@@assign` = scopes enforcement to specific service/resource types (e.g. `["secretsmanager:*"]`) — other services untouched even if noncompliant there. Key nuance: enforces *format* when tag present, doesn't force tagging — untagged resource not flagged noncompliant. Detects/reports violation via compliance dashboard (generate report listing tagged/noncompliant resources), doesn't block API call by default; pair w/ EventBridge to monitor/alert on noncompliant tags. Helps w/ Cost Allocation Tags + ABAC downstream. See [[Tagging]].

**EventBridge — Security (target auth: resource policy vs IAM role)** — Rule needs permission on target when it fires. Two methods, target type decides which: Resource-based policy targets — Lambda, SNS, SQS, S3 buckets, API Gateway — EventBridge attaches resource policy on target itself (e.g. Lambda policy statement "Allow EventBridge invoke"), no role needed. IAM role targets — Kinesis Data Streams, EC2 Auto Scaling, Systems Manager Run Command, ECS task — EventBridge assumes IAM role w/ permission to act on target, even though some of these (Kinesis) technically support resource policies, EventBridge doesn't yet use that path for them. Check EventBridge rule config to confirm which method active for given target.

**IAM Permission Boundaries** — advanced feature, supported for Users and Roles only (not Groups). A managed policy attached in special "boundary" slot (PermissionsBoundary field — console "Set permissions boundary", or CLI/API PermissionsBoundary param on CreateUser/CreateRole/PutUserPermissionsBoundary) — distinct from normal identity policy attachment (AttachUserPolicy/inline), even though both are just IAM policy JSON, same syntax. Boundary = ceiling/whitelist of max allowed actions, grants nothing by itself. Identity policy = actual grant. Effective permission = intersection (AND) of boundary + identity policy, not sum (OR) — action must be allowed in BOTH to work; allowed in only one → denied. Example: boundary allows s3:*/cloudwatch:*/ec2:*, identity policy allows iam:CreateUser only → iam:CreateUser not in boundary (blocked), s3/cloudwatch/ec2 not granted by policy (policy only grants iam:CreateUser) → zero actions in both sets → no permissions at all. Use case: cap what policies attached (even by mistake, e.g. AdministratorAccess) can ever grant a given user/role — e.g. junior IAM user boundary excludes IAM/billing actions permanently regardless of what policy gets attached later. Analogy: boundary = speed limit sign (doesn't move car), identity policy = gas pedal (illegal to floor past sign), need both to actually drive.

**AWS Organizations — SCP (Service Control Policy)** — org-level guardrail, attaches to Org root/OU/specific account, applies to entire AWS account (all IAM users/roles inside it, including account's own root user) — not attached to individual user/role directly like [[IAM Permission Boundaries]]. Same JSON policy syntax as IAM policy, different layer/scope. Sets max permissions ceiling for whole account, set by Org management account, can't be bypassed by member account's own admin/root. Combines w/ Permission Boundary + Identity-based policy: effective permission = intersection (AND) of all 3 — SCP ∩ Permission Boundary ∩ Identity policy. All three must allow same action → else denied. Diff vs Permission Boundary: SCP = account-wide ceiling (org-level control), Boundary = per-user/role ceiling (account-internal control). Use case: delegate responsibility to non-admins within their permission boundary (e.g. let a user create new IAM users, capped by their boundary). See [[IAM Permission Boundaries]].

**Parquet** — columnar storage format, born Twitter+Cloudera (Spark/Hadoop ecosystem, 2013). Same core idea as [[Columnar storage format (ORC/Parquet) vs row-based (CSV)]] — values grouped by column not row. Per-column compression + encoding (dictionary, run-length) → smaller files than CSV/JSON. Self-describing: schema (column names/types) embedded in file itself, no separate schema file needed. Supports nested/complex types (structs, arrays, maps) — good for semi-structured data flattened into columnar. vs ORC: near-identical purpose. ORC = Hive-native origin. Parquet = broader ecosystem adoption (Spark, Athena, BigQuery, Snowflake, pandas `.to_parquet()`) — de facto standard for data lakes. Exam: both interchangeable answers for "columnar format S3/Athena/Glue supports," unless question narrows via Hive vs Spark context.

**Shield Standard vs Shield Advanced** — Standard: free, automatic for every AWS account, no opt-in, covers layer 3/4 DDoS (SYN flood, UDP reflection/amplification, common network/transport attacks). Advanced: paid subscription, opt-in per resource (EC2/ELB/CloudFront/Global Accelerator/Route53), adds layer 7 (application-layer) DDoS detection/mitigation, cost protection (credits for scaling charges incurred during attack), 24/7 access to AWS DDoS Response Team (DRT), advanced CloudWatch metrics/attack diagnostics. Exam trap: "protect against DDoS" alone often satisfied by Standard (free, already on) — Advanced needed when question mentions layer 7, cost spike protection, or DRT engagement.

**DDoS Protection — layered edge architecture (exam pattern)** — best-practice answer combines multiple edge services, not one: CloudFront (or Global Accelerator if backend non-HTTP/not CloudFront-compatible) + AWS WAF (layer 7 filtering) + Shield (layer 3/4, or Advanced for layer 7) + Route 53 (DNS also at edge, also Shield-protected). All these run at AWS Edge locations — attack traffic absorbed/filtered far from origin/region, before reaching VPC. Behind edge layer: ALB/NLB spreads load across AZs, Auto Scaling Group absorbs remaining legitimate load spikes by scaling horizontally — counts as valid DDoS resiliency mechanism on exam, not just a scaling feature. Global Accelerator specifically: use when backend can't sit behind CloudFront (raw TCP/UDP apps, gaming, VoIP, non-HTTP) — gives static anycast IPs, still Shield-integrated at edge. See [[Shield Standard vs Shield Advanced]].

**AWS WAF vs Shield — layer split** — WAF operates layer 7 (HTTP/HTTPS) — filters requests via rules (SQLi, XSS, rate-based, IP Set allow/block, geo-match). Shield operates layer 3/4 primarily (network/transport) — Shield Advanced extends to layer 7. Don't conflate: WAF = app-layer firewall (you write/attach rules yourself), Shield = DDoS-specific protection (mostly automatic). Both can sit together in same architecture (e.g. CloudFront→WAF→origin, with Shield protecting the whole edge path). See [[Shield Standard vs Shield Advanced]], [[AWS WAF — IP Set]] if saved.

**DDoS Resiliency — Attack Surface Reduction (BP1/2/3/4/5/6)** — exam best-practice group: hide/obfuscate backend so attacker can't tell if it's Lambda/EC2/ECS behind. BP1 (obfuscate resources): CloudFront, API Gateway, ELB, Global Accelerator sit in front of compute — attacker only ever sees edge service. BP3: Route 53 also fronts DNS layer at edge. BP5 (network-level filtering): Security Groups + NACLs filter traffic by IP at subnet/ENI level; Elastic IPs get Shield Advanced protection. BP2/BP4 (protect API endpoints): API Gateway hides real backend (EC2/Lambda/other) — Edge-optimized mode = global reach built-in via CloudFront under hood, OR CloudFront + Regional mode = more manual control for DDoS tuning. Layer AWS WAF (BP2) in front of API Gateway for HTTP-layer filtering (SQLi/XSS/rate rules). API Gateway itself adds burst limits, header filtering, forced API keys — blunts DDoS at app layer. Net effect: attacker only ever touches edge (CloudFront/WAF/Global Accelerator/Route 53/API Gateway) — real compute (ASG instances in private subnet, BP7) stays invisible/unreachable directly. See [[DDoS Protection — layered edge architecture (exam pattern)]], [[AWS WAF vs Shield — layer split]], [[Shield Standard vs Shield Advanced]].

**Bastion Host vs NAT Instance/Gateway** — mirror-opposite purposes despite both sitting in public subnet. Bastion host: inbound door, lets humans SSH/RDP INTO private instances from internet, SG locked to admin IP only, modern replacement = SSM Session Manager (no open port). NAT instance/gateway: outbound door, lets private instances reach OUT to internet (updates/API calls), no unsolicited inbound allowed, private subnets route 0.0.0.0/0 through it, modern replacement = NAT Gateway (managed, HA, no patching). One sentence: bastion = inbound access for people, NAT = outbound access for instances.

**Ephemeral Port** — temp src port OS auto-assigns to client side of outbound connection (browser request, any client→server call). Range varies by OS: IANA/Windows 49152–65535, many Linux kernels 32768–60999. Why needed: every connection identified by 5-tuple (src IP, src port, dst IP, dst port, protocol) — client always hits server on fixed known port (443/80), but client-side port picked random from ephemeral range so OS can track many simultaneous connections (multiple tabs/apps) and multiple connections to same dst IP+port don't collide. Server response routed back using that exact ephemeral port from request. AWS relevance: NAT Gateway tracks (src IP, ephemeral port) mapping to route return traffic to correct private instance; Security Groups stateful (return traffic auto-allowed, no ephemeral rule needed); NACLs stateless — must explicitly allow ephemeral port range inbound for return traffic, common exam trap (NACL missing 1024-65535 inbound → connections break even though outbound rule looks fine). See [[Bastion Host vs NAT Instance/Gateway]].

**NAT Gateway — no cross-AZ failover** — NAT Gateway resides in single AZ, resilient only within that AZ — no automatic failover to another AZ if its AZ goes down. Private subnet routed through a NAT GW in a dead AZ loses internet access, no self-healing. Fix: deploy one NAT Gateway per AZ, each AZ's private subnet routes to its own AZ's NAT GW (not shared across AZs) — failure then stays contained to that AZ, since instances in the dead AZ are down too and don't need NAT anyway. Design implication: never route AZ-A private subnet through AZ-B's NAT GW — creates unnecessary cross-AZ dependency/cost, defeats the point of AZ isolation.

**NACL Rules — Ephemeral Ports (web tier ↔ DB tier example)** — NACLs stateless, need explicit rule BOTH directions, unlike SG. Setup: Web-NACL (public subnet) + DB-NACL (private subnet), client→RDS on port 3306. 4 rules needed total: Web-NACL outbound allow TCP 3306 to DB subnet CIDR (request leaves web subnet). DB-NACL inbound allow TCP 3306 from Web subnet CIDR (request reaches DB). DB-NACL outbound allow TCP ephemeral range (1024-65535) to Web subnet CIDR (response leaves DB, back to client's random ephemeral port). Web-NACL inbound allow TCP ephemeral range (1024-65535) from DB subnet CIDR (response reaches client). Miss ephemeral inbound rule on Web-NACL = classic break: outbound looks fine, DB request arrives, but response silently dropped at Web-NACL. See [[Ephemeral Port]].

**VIF (Virtual Interface)** — logical interface riding on top of physical Direct Connect connection. 3 types: Private VIF (connect to VPC via VGW/DXGW, private IP space), Public VIF (reach AWS public services — S3, DynamoDB etc — over public IP space, no internet needed), Transit VIF (connect to Transit Gateway). One physical DX connection can carry multiple VIFs (up to 50), each VIF = separate BGP session/VLAN. See [[Direct Connect — Resiliency (High vs Maximum)]].

**Direct Connect — Resiliency (High vs Maximum)** — 2 exam architectures for critical workloads. High Resiliency: 2 DX locations, 1 connection each (1 private VIF per location) → "one connection at multiple locations." Survives single DX location failure. Maximum Resiliency: 2 DX locations, 2 independent connections each = 4 connections total, terminating on separate devices. Exam phrase: "maximum resilience achieved by using separate connections terminating on separate devices in more than one location." Diff from High: doubles connections per location, not just locations. See [[VIF (Virtual Interface)]].

**Site-to-Site VPN throughput — VGW vs Transit Gateway (ECMP)** — VPN to Virtual Private Gateway: 1 VPN connection = 1 VPC only, max throughput 1.25 Gbps, connection made of 2 tunnels but no multi-path use (capped at single-tunnel-equivalent rate). VPN to Transit Gateway: 1 VPN connection = access to MANY VPCs (all attached to TGW, transitive routing). TGW also enables ECMP (Equal Cost Multi-Path) — routes traffic across both tunnels of the connection simultaneously → 1 VPN via TGW = 2.5 Gbps (vs 1.25 via VGW). Add more VPN connections into same TGW → throughput scales linearly via ECMP: 2x VPN = 5.0 Gbps, 3x VPN = 7.5 Gbps. Extra cost: $ per GB processed by TGW. Exam trigger: "need >1.25 Gbps VPN throughput" or "multiple VPN connections aggregate bandwidth" → Transit Gateway + ECMP, not VGW.

**Ingress vs Egress** — Ingress = inbound traffic into resource/network. Egress = outbound. Security Groups: ingress rules (allow inbound) + egress rules (allow outbound), stateful — response traffic auto-allowed both ways once initial direction permitted. NACLs: same ingress/egress split but stateless — need explicit rule both directions. Kubernetes/EKS context: Ingress = separate resource type, routes external HTTP(S) traffic into cluster services (different meaning than firewall rule direction).

**SSM (AWS Systems Manager)** — manage/configure EC2 + on-prem servers without SSH. Requires SSM Agent installed on instance + IAM role w/ SSM permissions. Key components: Session Manager (shell access via browser/CLI, no open SSH port, no bastion host needed), Run Command (run scripts/commands across many instances at once), Parameter Store (store config/secrets, plaintext or KMS-encrypted, free tier), Patch Manager (automate OS patching), State Manager (enforce config state on schedule).

**EC2-Classic** — original AWS network model, pre-VPC (before ~2013), retired Aug 2022. All instances shared one flat network — no isolation, no subnets, no custom IP ranges, no cross-account security-group referencing. Legacy/exam-trivia only now, VPC = standard model today.

**ClassicLink** — bridge feature, let EC2-Classic instances connect privately (via private IP) to a VPC during migration period. Dead now since EC2-Classic retired — historical/exam context only. See [[EC2-Classic]].

**VPC Endpoints vs NAT Gateway** — partial replacement, not full. VPC Endpoint (Interface = PrivateLink, Gateway = S3/DynamoDB) lets private subnet reach specific AWS services privately, no internet route/NAT needed for that traffic — cheaper, no NAT bottleneck. NAT GW still required for: outbound to non-AWS internet (external APIs, package repos etc), any AWS service w/o endpoint support. So endpoints cut NAT dependency for AWS-service traffic only, don't eliminate NAT GW unless zero internet-bound traffic from private subnet.

**Regional NAT Gateway (RNAT)** — newer NAT GW mode (announced Nov 2025). Standalone resource w/ own AWS-managed route table, NOT placed inside any subnet — no public subnet required at all. AWS runs it distributed across AZs automatically, expands/contracts w/ workload presence, no manual per-AZ NAT GW creation or route-table editing as VPC grows into new AZs. Contrast traditional NAT Gateway: must create public subnet, deploy NAT GW into it, one per AZ for HA, manual route table wiring per private subnet. RNAT = simplified/managed HA, traditional = manual per-AZ setup, both otherwise same job (private subnet outbound internet access via translated IP).

**NACL vs Security Group — stateless vs stateful** — "state" = connection tracking, a table remembering active connections (source IP/port/protocol). Security Group (stateful): tracks each connection when it's initiated — allow outbound request → SG remembers "this connection active" → reply traffic back in auto-permitted, no separate inbound rule needed. Only write rule for direction traffic originates; return path handled by tracking, not a rule. NACL (stateless): no connection memory, evaluates each packet independently against rule list. Outbound rule allowing traffic out does NOT auto-permit the reply packet coming back — treated as brand-new packet, needs own explicit inbound rule (often ephemeral port range 1024-65535, since client-side reply lands on random high port). This is why NACL needs explicit rules in both directions, SG doesn't.

**VPC Peering — cross-region/cross-account** — supported, both combinable same connection. Cross-account: peer VPC owned by different AWS account (accept request from other account). Cross-region (inter-region peering): peer VPC in different region, traffic encrypted, travels AWS backbone not public internet. Limits: no overlapping CIDR blocks between peered VPCs, no transitive peering (A↔B + B↔C ≠ A↔C, need direct A↔C peer), must manually update route tables both sides.

**Linux route table → home modem/router** — default route (`default via 192.168.0.1 dev wlp4s0`) = modem/router's LAN IP. Any packet destined outside local subnet (not matching 192.168.0.0/24) hits default route → sent to modem. Modem then NAT-translates private IP → public IP, forwards to ISP/internet. Route table's default route = literally "hand off to the modem" instruction.

**AWS Site-to-Site VPN vs consumer VPN (ProtonVPN etc)** — same underlying tech (encrypted IPSec-style tunnel), different shape/purpose. Consumer VPN (ProtonVPN): client-to-site, 1 device ↔ 1 VPN server, masks single device's IP/location, bypass censorship/geo-block — per-user anonymity tool. AWS S2S VPN: site-to-site, connects ENTIRE on-prem network (via Customer Gateway) to ENTIRE VPC (via Virtual Private Gateway) over encrypted tunnel across public internet — many devices both sides, always-on infra link, not per-user anonymity. Closer consumer analogy = router-to-router VPN linking two office branches, not single-device client VPN.

**ICMP (Internet Control Message Protocol)** — not for data transfer, no TCP/UDP port, no app payload — used for network diagnostics/error messages between hosts. `ping` = tool using ICMP Echo Request/Reply message type specifically (ping ⊂ ICMP, not equal — ICMP also carries Destination Unreachable, Time Exceeded [used by traceroute], Redirect, etc). AWS context: SG default denies all inbound unless explicit rule — a rule allowing TCP port 22/80 does NOT cover ICMP, separate protocol. Need explicit inbound rule (Type: ICMP, or "All ICMP") for `ping` to reach EC2 instance from on-prem/elsewhere, even if instance otherwise fully reachable via SSH/HTTP.

**AWS VPN CloudHub vs plain Site-to-Site VPN** — same tech (IPSec S2S VPN), different topology. Plain S2S VPN: 1 on-prem site ↔ 1 VPC, one Customer Gateway ↔ one Virtual Private Gateway, point-to-point. CloudHub: multiple on-prem sites, EACH gets own S2S VPN connection into the SAME VGW — not new tech, just several S2S connections terminating on one VGW. Side-effect: those sites can then reach each other too (not just the VPC), routed through shared VGW as hub. See [[Hub-and-spoke topology]].

**Hub-and-spoke topology** — central node (hub) everyone connects to; other nodes (spokes) don't connect directly to each other, only to hub. Spoke-to-spoke traffic must route through hub first (A→hub→B, no direct A-B link). Fewer total connections needed vs full mesh (N spokes = N links, not N² mesh links), but hub becomes single point of dependency/bottleneck. AWS VPN CloudHub: VGW = hub, branch offices = spokes, each own VPN link to VGW only.

**Bastion host SG — source CIDR** — bastion in public subnet, developers connect over internet, so SG source must be company's **public** CIDR (office's internet-facing/NAT IP), not private CIDR (internal-only, not routable over internet, never seen as inbound source). Port 22 (SSH), not 80 — bastion is for admin shell access, not web traffic. Backend EC2 SG in turn allows only from bastion (not from internet) — bastion = single controlled entry point into private subnet.

**VPC CIDR choice when connecting networks later** — pick CIDR that (1) doesn't overlap any existing/soon-to-be-connected network (corp, satellite office, other VPCs) — overlapping ranges can't be routed between via peering/VPN, and (2) fits AWS's allowed VPC size, /16 to /28 (so /12 too big even if non-overlapping → invalid). Check candidate CIDR falls fully outside each existing block's range, not just "different first octet."

**VMware Cloud on AWS** — bridges on-prem VMware (vSphere/vSAN/NSX hypervisor stack, managed via vCenter dashboard) into AWS: AWS sells bare-metal servers, VMware installs same hypervisor stack on them inside AWS datacenter. Same vCenter console then manages BOTH on-prem VMs + these AWS-hosted VMs — no need learn EC2-native tooling. Use cases: (1) lift-and-shift migration — VM built for VMware drops onto AWS-hosted VMware host unchanged, no rebuild for EC2 format. (2) hybrid/multi-DC prod — split workloads on-prem + AWS, one pane of glass. (3) DR — replicate VM to AWS side, failover fast using same familiar tooling mid-crisis. Bonus: VMware host physically sits inside AWS network, so VMs can reach native AWS services (S3, RDS, Direct Connect, Redshift, FSx) directly — stepping stone toward eventual full-native AWS migration at own pace. Exam: know it's VMware-on-AWS-hardware bridge for migrate/hybrid/DR, not internals of vSAN/NSX.

**AWS Application Discovery Service — Agentless vs Agent-based** — earlier planning step before actual migration (MGN does the migration itself, ADS just inventories what you have). Agentless discovery: no install on VM, reads via host/hypervisor layer (e.g. vCenter for VMware) — gets VM inventory, config, basic perf history (CPU/mem/disk). Fast setup, zero footprint on guest OS, but blind to what's happening INSIDE the VM. Agent-based discovery: small agent installed inside each server's OS (Linux/Windows) — sees inside guest: running processes, detailed perf, and network connections between servers (who talks to who, what port). Needed for dependency mapping in multi-tier app migrations (DB↔app↔web tiers must move together/right order). More setup + touches prod OS, but only agent-based reveals cross-server dependencies. Rule: agentless = "what VMs exist, how big/busy." Agent-based = "what runs inside, what depends on what."

**ENA vs EFA (Enhanced Networking)** — EFA = ENA + OS-bypass, for HPC/tightly-coupled cluster placement group workloads needing low-latency node-to-node comm — use over plain ENA when question mentions HPC/MPI/cluster placement group. ENA (Elastic Network Adapter): enhanced networking driver, up to 100 Gbps, optimizes bandwidth, general high-throughput use. EFA (Elastic Fabric Adapter): built on ENA, adds OS-bypass hardware interface + libfabric, optimizes latency (not just bandwidth) for tightly-coupled parallel workloads.

**SPF / DKIM (email anti-spoofing, SES)** — both DNS-based mechanisms proving email legit, not spoofed. SPF (Sender Policy Framework): DNS TXT record on domain lists which mail servers/IPs authorized send mail for that domain. Receiver checks sending IP against list — not listed → fail/spam/reject. DKIM (DomainKeys Identified Mail): cryptographic signature attached to email header, signed w/ private key (domain owner holds), public key published in DNS. Receiver verifies signature w/ public key → confirms email untampered + genuinely from claimed domain. Diff: SPF validates sending IP allowed, DKIM validates content integrity/authenticity via signature. Often paired w/ DMARC (policy: what to do when SPF/DKIM fail). SES supports both — configure on sending domain so SES-sent mail passes verification, avoids spam folder.

**STS (Security Token Service)** — AWS service issuing temp creds. Flow: caller invoke `AssumeRole` on target role ARN → STS check role's trust policy (who allowed assume it) → if allowed, return temp access key + secret key + session token, valid 15min–12hr (configurable). Backs: cross-account access (assume role in another account instead of creating IAM user there), identity federation (SAML/Google login → temp AWS creds), EC2/Lambda instance roles (auto-rotated temp creds under hood).

**EBS — Delete on Termination (root vs extra volumes)** — flag controlling whether attached EBS volume auto-deletes when its EC2 instance terminates. Root volume: default = true (deletes w/ instance) — this is why people expect EBS = fully persistent but lose root data on terminate. Extra (non-root) volumes: default = false (survive termination, stay as orphaned volume, reattach elsewhere). Flag configurable per-volume at launch (or edit before terminate) — flip root to false if need it survive. Redshift OLTP vs OLAP: Redshift shares Postgres SQL syntax/wire protocol but internals rewired for OLAP (columnar storage, MPP parallel query, compression) — not for transactional row-by-row writes. **OLTP** (RDS/Aurora/DynamoDB): many small fast transactions, row-based storage, day-to-day app backend. **OLAP** (Redshift/Athena): few huge analytical queries scanning millions rows, column-based storage (read only needed columns), reporting/BI/data warehousing.

**EC2 root volume — what it is & why called root** — EC2 instance itself has no own persistent storage (compute only, borrowed CPU/RAM from host). At launch, AMI boots OS onto a disk — that disk = root volume, holds `/` (Linux root filesystem, same term as laptop's root partition). Not "attaching to existing storage" — it's the instance's only/primary disk from moment 1. EBS-backed AMI (default, all modern instance types — Amazon Linux, Ubuntu, Windows, etc): root volume auto-created as EBS volume (network-attached block storage) at launch, no way to skip it, editable size/type in launch wizard but always created. Instance store-backed AMI: legacy/EOL, Linux-only, restricted to old instance types (C1/C3/D2/I2/M1/M2/M3/R3/X1) — root lives on physical host disk instead, not usable for new deployments. Practical rule: launching EC2 today = root EBS volume created automatically, basically no alternative. See [[EBS — Delete on Termination (root vs extra volumes)]].

**Cross-account access: IAM role vs new IAM user (why role wins)** — delegating access to resources in another AWS account. Bad approach: create new IAM user in target account, share its access key+secret with the outside users. Static, long-lived creds, travel via email/chat/plaintext = leak risk (anyone who intercepts or finds in history has permanent access until manually rotated), plus manual rotation burden. Right approach: create IAM role in target account w/ needed permissions, trust policy lets source-account users assume it. Users call [[STS (Security Token Service)]] `AssumeRole`, get temp session creds (expire automatically), no static secret ever created or shared. Exam pattern: "delegate access to another account's resources" → IAM role + AssumeRole, never new IAM user with shared creds.

**Cross-account access — both sides required (identity policy + resource policy or role trust)** — Service A (account X) accessing Service B (account Y) always needs permission granted on BOTH sides, mechanism depends on whether B supports resource-based policies. Identity policy: attached to IAM user/role (the caller), every AWS service has this — exists everywhere. Resource policy: attached directly to the resource itself (e.g. S3 bucket policy, SNS topic policy, SQS queue policy, KMS key policy, Lambda resource policy) — only SOME services support this. Case 1 — target supports resource policy (S3, SNS, SQS, KMS, Lambda, ECR, Secrets Manager): grant caller's identity policy access AND target's resource policy must explicitly allow account X/caller's role. Skip either side → access denied. Example: Lambda in account A reading S3 bucket in account B needs Lambda execution role IAM policy allowing s3:GetObject AND bucket policy in account B allowing that role. Case 2 — target has NO resource policy option (EC2, RDS, DynamoDB): can't attach cross-account permission directly to resource. Instead account Y creates IAM role w/ needed permissions, trust policy allows account X to assume it (`sts:AssumeRole`), account X's caller needs identity policy permission to assume that specific role ARN. Caller assumes role → gets temp creds → acts as that role inside account Y → resource-level permissions apply normally (regular identity-policy check, no resource policy needed since caller is now "inside" account Y). So mechanism differs (resource policy vs assumable role) but always two-sided: something in source account granting the call, something in target account accepting it.

**Domain registrar vs DNS service — decoupled roles** — two separate jobs often bundled by default, confusing bc they don't have to stay together. Registrar (Namecheap, GoDaddy, Amazon Registrar): owns registration of the domain NAME itself, handles yearly renewal fee, is who's listed in WHOIS. DNS service (Route 53, Cloudflare, or registrar's own default): actually ANSWERS "what's the IP for this domain" — holds the A/AAAA/CNAME/alias records. Link between them = NS (nameserver) records: registrar tells the .com TLD registry "my domain's NS = X" — X is whichever DNS service you pointed at. Resolution chain: client → recursive resolver → root servers → TLD servers → NS records (registrar-set) → that DNS service answers w/ actual A/CNAME record → client gets IP. Default: registrar auto-assigns its own NS, becomes DNS service too (convenience). Swap NS records to Route 53/Cloudflare → registrar stays registration-only, that other service now answers all DNS queries for the domain — no domain transfer needed, pure DNS handoff. Two modes of pointing elsewhere: (1) full NS swap — hands off ALL records for the domain to new DNS service (e.g. Cloudflare Pages setup: paste Cloudflare's 2 NS values into Namecheap's nameserver field). (2) single record only — keep registrar's default DNS, just add one CNAME/A record pointing a specific (sub)domain at the other service's target, rest of domain's records (email etc) stay with registrar's DNS. Exam pattern: "migrate DNS to Route 53 without transferring domain" = swap NS records only, registrar unchanged.

**S3 access — same-account (OR) vs cross-account (AND)** — principal accessing S3 object needs identity policy (IAM) allow OR bucket policy (resource policy) allow — but which logic applies (OR vs AND) depends on whether principal is in the bucket owner's account. Same account: OR — single authority (the account) already trusts both sides, so either IAM policy on principal, or bucket policy naming principal, alone suffices. Cross account (principal in different AWS account than bucket owner): AND — two separate authorities, each must sign off independently. Bucket owner's bucket policy must explicitly allow the external account/principal (the invite), AND external principal's own IAM policy must allow the S3 action (their home account must also permit the trip) — IAM policy alone never reaches into another account's resource by default. Missing either side → deny. Explicit Deny anywhere (IAM, bucket policy, SCP) always overrides any Allow, both cases. See [[Cross-account access — both sides required (identity policy + resource policy or role trust)]] — same underlying rule, S3 is the resource-policy-supporting case (Case 1) there.

**S3 Event Notifications — Resource Access Policies (SNS/SQS)** — S3 publishes events (ObjectCreated, ObjectRemoved) to SNS topics, SQS queues, or Lambda functions. S3 itself is an AWS-managed service, doesn't "assume" an IAM role to make these calls — instead, S3 calls SNS/SQS/Lambda APIs on your behalf AS THE S3 SERVICE. So you can't solve permission with an S3-side IAM role (S3 doesn't have one to grant). Instead, SNS/SQS/Lambda must have a **resource-based policy** explicitly allowing S3 service to publish/send messages. SNS Topic Policy: allows S3 service principal to SNS:Publish to that topic. SQS Queue Policy: allows S3 service principal to SQS:SendMessage to that queue. Lambda Resource Policy: allows S3 service to Lambda:InvokeFunction. These resource policies protect the receiving service: they say "only allow these specific callers (S3 from this bucket, or other services)." The distinction: IAM role-based (identity-based) permission says "this principal can do X." Resource-based permission says "this resource accepts calls from X." S3 event delivery needs the second type. Why it matters: cross-service permissions require BOTH sides — one service initiating (S3, already managed), and the target granting acceptance. Miss the resource policy on SNS/SQS → S3 publishes but messages silently drop, never reach queue/topic. Least-privilege: resource policy locks down "only S3 from bucket-X can post here," preventing accidental event leaks if another service later tries same path.

**DR strategy ladder — Backup&Restore vs Pilot Light vs Warm Standby vs Multi-Site Active-Active** — 4 standard AWS DR strategies, ranked cheapest/slowest → priciest/fastest. Backup & Restore: just backups (e.g. AWS Backup, S3), no standing infra in DR region, rebuild from scratch on disaster — cheapest, RTO/RPO = hours. Pilot Light: core infra (e.g. DB replica) always running minimal/small in DR region, but application servers exist as STOPPED EC2 instances or unprovisioned — on disaster, START the stopped instances and scale up, RTO = ~10s of minutes. Warm Standby: full copy of production stack RUNNING at reduced/scaled-down capacity in DR region, ALREADY serving a portion of live traffic (or ready to immediately) — on disaster, scale up capacity and shift 100% traffic over, RTO = minutes. Multi-Site Active-Active: full production-scale stack running in 2+ regions simultaneously, all serving live traffic all the time, near-zero RTO/RPO — most expensive. Exam trigger words: "instances exist but are stopped/off, start them on failover" = Pilot Light. "Already running and serving some live traffic, scale up on failover" = Warm Standby. Easy to confuse these two — the tell is whether the DR-region compute is OFF (pilot light) or ON-and-serving-traffic (warm standby).

**Amazon Security Lake** — centralizes security telemetry (VPC Flow Logs, CloudTrail, Route53 logs, GuardDuty findings, 3rd-party sources) into a single S3-backed data lake, normalizes it into Open Cybersecurity Schema Framework (OCSF) format automatically, across multiple AWS accounts/regions/Organizations. Purpose: give a security team one queryable place (via Athena/QuickSight/SIEM tools) instead of hunting logs across many services/accounts separately. Not a detection engine itself (that's GuardDuty) — Security Lake is the aggregation/normalization/storage layer that other tools then query or subscribe to.

**EC2 Instance Hibernate** — stop action that PRESERVES the in-memory (RAM) state to the root EBS volume before shutting down, instead of discarding it like a normal Stop. On next Start, RAM contents restored from EBS, OS resumes exactly where it left off (running processes, open connections/state) — much faster than cold boot + app re-initialization. Use case: long-running jobs (ML training/inference, big in-memory caches) that need to pause without losing in-memory state, or cost savings by stopping idle-but-stateful instances overnight. Requires: root volume must be EBS (not instance store), volume large enough to hold RAM contents, and enabled at launch time (can't retrofit onto a running instance not originally configured for it). Contrast plain EC2 Stop: RAM discarded, only disk state (EBS) persists, app must fully re-initialize on next Start.

**EFS Standard-IA / EFS One Zone-IA** — EFS's own Infrequent Access storage classes, distinct from S3-IA (separate service, don't conflate). Same EFS filesystem, EFS Lifecycle Management auto-moves files unaccessed for N days (e.g. 30/60/90) from EFS Standard → EFS Standard-IA (~92% cheaper storage, small per-access retrieval fee, still Multi-AZ durability) or → EFS One Zone-IA (single-AZ, even cheaper, for non-critical/recreatable data). Files move back to Standard automatically on next access (unlike S3 which needs explicit restore for some classes). Good exam pattern: "reduce EFS storage cost for rarely-accessed files, no manual intervention" → enable EFS Lifecycle Management to Standard-IA.

**S3 Access Points** — named network endpoints attached to a bucket, each with its own IAM policy, used to give each application/team/service its own scoped access path into a SHARED bucket instead of managing one increasingly-complex bucket policy juggling everyone's permissions. Example: one central logs bucket, 5 analytics services each need different prefixes/permissions → create 5 Access Points (e.g. `access-point-team-a`, `access-point-team-b`), each with its own policy scoped to what that team needs, instead of one giant bucket policy with 5 different conditional blocks. Each access point has its own DNS name/ARN, can also restrict to a specific VPC (VPC-only access points, blocks public internet access to that specific path). Exam trigger: "multiple consumers need different scoped access to the same bucket, simplify permission management" → S3 Access Points, not one complex bucket policy.

**Amazon MQ** — fully managed MESSAGE BROKER service (ActiveMQ or RabbitMQ engine), NOT the same category as SQS/SNS. Use case: migrating an EXISTING on-prem application that already uses a standard messaging protocol (JMS, AMQP, MQTT, STOMP, OpenWire) and a broker like ActiveMQ/RabbitMQ — Amazon MQ is drop-in compatible, minimal app-code rewrite. Contrast SQS/SNS: AWS-native, proprietary APIs, no drop-in compatibility with existing broker-based apps — better for new cloud-native designs, not lift-and-shift of existing broker-dependent systems. Exam trigger: "migrate existing app using [ActiveMQ/RabbitMQ/JMS/AMQP], minimize code changes" → Amazon MQ. "New application, need decoupling, no existing broker dependency" → SQS/SNS.

**VPC Sharing (AWS Resource Access Manager / RAM)** — lets a central/owning AWS account share specific VPC SUBNETS with other AWS accounts in the same AWS Organization, via AWS RAM. Participant accounts can launch their own resources (EC2, RDS, etc) directly INTO the shared subnets, as if the subnet were their own — but they can't modify the VPC/subnet itself (routing, NACLs, gateways stay controlled by owning account). Different from VPC Peering (connects two SEPARATE VPCs, each account keeps its own VPC) and Transit Gateway (hub-and-spoke connecting many separate VPCs) — VPC Sharing is ONE VPC, resources from MULTIPLE accounts living inside it directly. Use case: central networking team owns/manages the VPC (IP plan, security, routing), individual app teams just deploy resources into their assigned shared subnet — centralizes network governance while keeping account-level resource isolation for billing/access. Exam trigger: "multiple AWS accounts, shared services VPC, centralize VPC management, resources need to share the same subnets" → VPC Sharing via RAM, not Peering/Transit Gateway.

**gp3 baseline IOPS — free performance floor** — gp3 EBS volumes include 3,000 IOPS and 125 MB/s throughput baseline, INCLUDED FREE regardless of volume size (unlike gp2, where IOPS scale with size at 3 IOPS/GB and small volumes get poor baseline performance). Need more than baseline? Provision additional IOPS (up to 16,000) and throughput (up to 1,000 MB/s) on gp3 for an incremental cost — still usually cheaper than an equivalent io1/io2 Provisioned IOPS volume. Exam pattern: "need moderate IOPS (≤3,000), most cost-effective EBS option" → gp3 at whatever size needed, don't over-reach for Provisioned IOPS (io1/io2) when gp3's free baseline already covers the requirement.

**Amazon Macie** — machine-learning-based sensitive data DISCOVERY/CLASSIFICATION service, scoped to Amazon S3 ONLY (does not scan RDS, DynamoDB, or other data stores directly). Scans S3 buckets, identifies PII/financial/credential-like patterns, produces findings (dashboards, alerts) showing WHERE sensitive data lives and what type. Does NOT mask, redact, transform, or remove data itself — it's a reporting/visibility tool, not a data-transformation tool. Exam trap: question asks to "discover AND mask/anonymize" sensitive data → Macie alone is wrong (only does the discover half); pair with or replace by a transform tool like AWS Glue DataBrew for the masking step. See [[AWS Glue DataBrew]].

**AWS Glue DataBrew** — visual, no-code data preparation/cleaning tool. Connects to various data sources (S3, RDS, Redshift, etc.), lets you build a "recipe" of transformation steps (filter, format, dedupe, and — key exam point — MASK/replace sensitive fields like names, SSNs) using pre-built recipe steps, no code required. Exports cleaned/transformed data back out (e.g. to S3). Exam trigger: "weekly export with PII masked/anonymized, minimize custom code" → DataBrew (has ready-made masking recipes + connects directly to RDS/other sources) — contrast Macie, which only discovers/classifies sensitive data in S3 but has no masking/recipe capability. See [[Amazon Macie]].

**API Gateway — Throttling** — API Gateway caps request rate so backend (Lambda/EC2/DB) isn't overwhelmed by spikes. Token bucket model: rate limit = steady requests/sec (e.g. 1,000 rps), burst limit = short spike allowed above rate (e.g. 2,000 for a few seconds). Over limit → request rejected with HTTP 429 Too Many Requests; AWS-generated client SDKs auto-retry on 429. Levels: account-level default per region, per-stage/per-method overrides, per-client via usage plans + API keys. Why "API Gateway auto-scales, do nothing" is wrong: API Gateway itself scales, but the backend behind it does not scale infinitely — throttling protects the backend, not API Gateway. Exam trigger: "protect backend from traffic spikes" + API Gateway → throttling (+ caching to cut backend calls further). Wrong answers: move to EC2+ELB+ASG (rearchitecture, unnecessary), CloudFront in front (speeds delivery, doesn't shield backend much), Lambda in VPC (irrelevant). See [[API Gateway — caching layer]].

**API Gateway — Canary Release** — built-in deployment feature on an API stage: new version deployed to a "canary" slice of the SAME stage, a configured % of traffic (e.g. 10%) goes to canary, rest stays on current version. Monitor canary metrics/logs separately, raise % gradually, then promote canary → becomes full production. Roll back = just set canary % to 0. Cheap: no second environment, no DNS change, same custom domain. Contrast blue/green: two full environments running side by side, then switch — more infra, more cost. Exam trigger: "new API version, minimal customer disruption, MOST cost-effective" + API Gateway → canary release, not blue/green. Swapping to a new API Gateway behind the same custom domain = DNS propagation delays/disruption.

**CloudFront Signed URLs vs Signed Cookies** — both restrict private content on CloudFront to authorized users (e.g. paying subscribers), same security model: signed with a trusted key group key pair, can carry expiry time + IP range restrictions (custom policy). Signed URL: signature embedded in URL query string, one URL = one file. Use when: restricting access to individual files (e.g. one installer download), or client doesn't support cookies (custom HTTP client). Signed Cookies: app sends `Set-Cookie` headers to the authorized viewer once, browser then attaches cookies to every request, all matching files unlocked. Use when: access to MULTIPLE restricted files (all segments of an HLS video, whole members-only area of site), or you DON'T want to change current URLs (URL stays clean, auth lives in cookie). Exam keywords: "multiple files" or "don't change URLs" → Signed Cookies. "single file" or "client without cookie support" → Signed URL. Pair either with [[OAC (Origin Access Control)]] so users can't bypass CloudFront by hitting S3 directly. Wrong-answer traps: Field-Level Encryption (encrypts specific form fields e.g. card numbers from viewer to origin with public key, only app at origin can decrypt — protects data, not access), Origin Protocol Policy "Match Viewer" (CloudFront→origin uses HTTP or HTTPS matching what viewer used — transport setting, zero auth), Signed URL when question says "multiple files" + "don't change URLs" (signature in query string = URL changes, per-file). Not in slides v48 (only S3 Pre-Signed URLs p.329, CloudFront section pp.335–344).

**AWS Artifact** — self-service portal for AWS's OWN compliance documents: audit reports (SOC 1/2/3, PCI DSS, ISO certifications, etc.) + agreements (BAA for HIPAA, NDA). Download on demand from console, free, available to all accounts (non-admin IAM users need explicit Artifact permission). Doesn't scan anything or assess your resources — it's a document library proving AWS's side of shared responsibility to your auditors. Exam trigger: "auditors need AWS compliance/security reports" → Artifact. Wrong answers: Amazon Inspector (vulnerability scanning of YOUR EC2/ECR/Lambda workloads), Security Hub (aggregated security findings + posture score across accounts), AWS Config (tracks YOUR resource config compliance vs rules), IAM (access control, holds no reports).

**SAML 2.0 Federation (AD FS) vs Web Identity Federation** — both let users sign in to AWS with an EXTERNAL identity instead of creating IAM users; both end with [[STS (Security Token Service)]] issuing temporary credentials for an IAM role. SAML 2.0 federation: for CORPORATE directories. Company's identity provider (IdP) — e.g. Microsoft Active Directory Federation Services (AD FS, part of Windows Server), Okta, Shibboleth — authenticates employee with on-prem/AD credentials, sends a SAML assertion to AWS, AWS trusts it (IAM SAML provider set up both sides), user gets console or API access via `AssumeRoleWithSAML`. Modern managed option: IAM Identity Center connected to AD. Web Identity Federation: for CONSUMER logins — Login with Amazon, Google, Facebook, any OpenID Connect (OIDC) provider — typically mobile/web app end users, usually via Cognito Identity Pools (`AssumeRoleWithWebIdentity`). Exam trigger: "on-prem Active Directory credentials, access AWS, no IAM users" → SAML 2.0 + AD FS. "Social login for app users" → Web Identity Federation / Cognito. Distractor trick: "SAML 2.0-based federation by using Web Identity Federation" mixes the two — wrong.

**AWS Control Tower vs Organizations vs RAM** — 3 multi-account services, distinct jobs, commonly used as distractors for each other. AWS Organizations: consolidates many accounts into one org — consolidated billing, OUs, SCPs. The foundation layer. AWS Control Tower: automated SETUP + GOVERNANCE of a multi-account environment ("landing zone") built on top of Organizations — pre-configured best-practice account structure, guardrails/controls (preventive via SCPs, detective via Config), account factory to vend new accounts, compliance dashboard. Does NOT share resources, does NOT build data lakes. AWS Resource Access Manager (RAM): SHARES specific resources owned by one account with other accounts/OUs/whole org — subnets ([[VPC Sharing (AWS Resource Access Manager / RAM)]]), Transit Gateways, Route 53 Resolver rules, License Manager configs, etc. Free. Avoids duplicating the same resource in every account. Exam triggers: "share resources across accounts" → RAM (+ Organizations). "Set up/govern new secure multi-account environment with guardrails" → Control Tower. "Consolidated billing / central policy" → Organizations.

**AWS Lake Formation** — service to BUILD, SECURE, and SHARE a data lake on S3 with minimal manual work. Registers existing S3 locations, uses Glue Data Catalog for schema + crawlers, [[AWS Lake Formation — Blueprint]] workflows for ingestion. Key feature = centralized fine-grained permissions: grant/revoke at database/table/COLUMN/row level (not just bucket/object like S3 policies) to IAM users, roles, or federated AD users — applied consistently whether queried via Athena, Redshift Spectrum, EMR, or Glue. Cross-account data sharing built in, free. Exam trigger: "central data lake, data from multiple accounts/sources, access by user role, minimal overhead" → Lake Formation. Wrong answers: Firehose per account (costly, it's streaming delivery), custom Lambda copy jobs (high overhead), Control Tower (account governance, not data).

**RDS IAM DB Authentication** — log in to RDS MySQL/PostgreSQL (and Aurora) with a short-lived AUTH TOKEN instead of a stored DB password. App calls RDS API (`generate-db-auth-token`) using its IAM credentials — e.g. the EC2 instance profile role — gets token valid 15 min, passes it as the password. Must be ENABLED on the DB instance + DB user mapped to IAM auth + IAM policy allowing `rds-db:connect`. Benefits: no password stored in app/DB, access managed centrally in IAM, connection forced over SSL. Exam trigger: "RDS access only via authentication token tied to EC2 instance profile credentials" → enable IAM DB Authentication. Wrong answers: "IAM + STS temporary token" (generic STS creds don't authenticate to MySQL itself), "IAM role on EC2" alone (role needed but DB must have IAM auth enabled), SSL alone (encryption, not authentication). Not supported for most other engines (Oracle, SQL Server) or DocumentDB-style DBs.

**EFS Lifecycle Management — limits (vs S3 Lifecycle)** — EFS lifecycle only MOVES files between storage tiers: Standard → Infrequent Access (IA) → Archive, and back to Standard on access. Transition triggers based on days since last access, max 365 days. It NEVER deletes files. S3 Lifecycle: transition actions (move to Standard-IA/Glacier/etc) AND expiration actions (delete objects, delete old versions) — no 365-day cap, can transition after 730+ days. Exam traps: "auto-delete files after 30 days" → S3 lifecycle expiration rule, not EFS (EFS can't delete; would need a cron job = overhead). "Move files older than 2 years to cheaper storage" → S3 lifecycle, EFS can't wait that long. AWS Transfer Family has no retention/delete setting either — deletion rules live on the S3 bucket. See [[EFS Standard-IA / EFS One Zone-IA]].

**AWS Data Transfer Terminal** — physical AWS facility (network-ready room) you book a reservation for in the console, show up with your OWN storage devices (drives, NAS, portable arrays), plug into AWS's high-bandwidth network, upload straight into S3 and other AWS services. Leave, room re-secured for next customer. Bypasses your slow office internet entirely. Replaces Snowball Edge for new customers (Snowball Edge no longer offered to them), so newer practice tests use DTT where old ones used Snowball — same logic. Exam trigger: "one-time bulk import, tens/hundreds of TB, current bandwidth would take weeks/months, fastest + cheapest" → Data Transfer Terminal (or Snowball if that's the option). Wrong answers: Direct Connect (weeks to provision, ongoing monthly cost, meant for permanent links, not one-off jobs), S3 Transfer Acceleration / DataSync / direct upload (all still limited by YOUR bandwidth), Storage Gateway (ongoing hybrid access, not bulk move). Can't stream ongoing changes — physical, one-shot. See [[DMS vs DataSync]].

**Amazon Data Lifecycle Manager (DLM) vs AWS Backup** — both automate backups, different scope. DLM: EBS-only (+ EBS-backed AMIs). Policy = target volumes/instances by TAG, schedule (e.g. every 12h), retention (keep last N / N days) — creates, keeps, and DELETES old snapshots automatically. No extra cost beyond snapshot storage. Built into EC2 console. AWS Backup: centralized backup service across MANY services (EBS, EC2, RDS, Aurora, DynamoDB, EFS, FSx, S3, Storage Gateway...), backup plans, vaults, Vault Lock (WORM), cross-region/cross-account copy, org-wide policies via Organizations. Exam trigger: "automate EBS snapshots, fastest, cost-effective, simple" → DLM. "Central backup across multiple services / accounts / compliance retention" → AWS Backup. Wrong answer: cron job calling `create-snapshot` via CLI (custom script = overhead, you manage deletion yourself).

**Route 53 — Geoproximity vs Geolocation Routing** — both route by WHERE the user is, different control. Geolocation: fixed mapping by continent / country / US state → specific resource (e.g. all of Germany → eu-central-1). Use for: content localization, legal/licensing restrictions ("EU users must hit EU servers"), need a default record for unmatched locations. Can't resize areas. Geoproximity: routes by physical DISTANCE between user and resources (AWS regions or lat/long coordinates), plus a BIAS value (-99 to +99) that expands (+) or shrinks (-) the geographic area a resource serves → shifts a bigger or smaller slice of users to it. Requires Route 53 traffic flow. Exam trigger: "route a LARGER/SMALLER portion of traffic from an area to region X" or "shift boundary" → geoproximity + bias. "Users from country X must go to region Y" → geolocation. Other policies: latency (lowest latency region, not location), weighted (% split, ignores location), failover (active-passive), multivalue (up to 8 healthy records), IP-based (by client CIDR). See [[Route 53 — IP-Based Routing Policy]].

**AWS Storage Gateway — Tape Gateway** — Storage Gateway type that presents VIRTUAL tape library (VTL) over iSCSI to your existing on-prem backup software (Veeam, Veritas NetBackup, Commvault...), so backups go to AWS instead of physical tapes, no change to backup workflow. Virtual tapes stored in S3, ARCHIVED tapes moved to S3 Glacier Flexible Retrieval or S3 Glacier Deep Archive (cheapest). Other Storage Gateway types: S3 File Gateway (NFS/SMB file shares backed by S3), FSx File Gateway (local cache for FSx for Windows), Volume Gateway (iSCSI block volumes, cached or stored mode, snapshots to EBS). All Storage Gateway types = ongoing HYBRID access with local cache, not bulk one-time migration. Exam trigger: "replace on-prem tape backups" + "long retention (7–10 yrs), rarely accessed, cheapest" → Tape Gateway → Glacier Deep Archive. "Move historical files to AWS, one-way" → DataSync (can write directly into Deep Archive storage class), not Storage Gateway.

**Amazon SWF (Simple Workflow Service)** — older managed service for coordinating multi-step work across distributed components. Tracks workflow state, assigns tasks to "workers" and "deciders" — workers are YOUR code, can run on EC2, on-prem servers, anywhere with internet access, they poll SWF for tasks. Guarantees each task assigned once, no duplicates. Supports human/manual steps, long-running workflows (up to 1 year). Today mostly replaced by Step Functions for new builds (visual state machine, serverless, native AWS integrations). Exam trigger: "decoupled architecture using BOTH on-prem servers and EC2" → SQS + SWF (both are decoupling services workers anywhere can poll). "Human approval step / external signals in workflow" → SWF (or Step Functions with callbacks). Wrong answers: RDS/DynamoDB (databases, don't decouple), VPC peering (VPC↔VPC only, can't peer with on-prem).

**Cost Allocation Tags** — tags (key/value, e.g. `Department=Finance`) applied to resources that you then ACTIVATE in the Billing and Cost Management console → billing reports + Cost Explorer can group/filter costs by that tag. Two kinds: AWS-generated (e.g. `aws:createdBy`, activate them too) and user-defined. Tagging alone does NOTHING for billing until activated; only costs incurred AFTER activation show up. Exam trigger: "break down / report monthly costs per department, cost center, project, team" → tag resources + activate cost allocation tags. Wrong answers: AWS Budgets (alerts/actions when thresholds crossed, not a breakdown), Cost Explorer resource filter (limited, not by department), Cost and Usage Report alone (per service/usage, needs tags to split by department). Savings Plans / RIs = pricing discounts, no allocation.

**NLB — Static IP / Elastic IP for Whitelisting** — Network Load Balancer (layer 4, TCP/UDP/TLS) gets ONE static IP per AZ, and you can assign your own Elastic IP per AZ (even Bring Your Own IP, BYOIP). ALB (layer 7, HTTP/HTTPS) has NO static IP — its IPs change, you only get a DNS name, can't attach EIP. Need ALB features + static IP → put NLB in front of ALB (ALB-type target group) or use Global Accelerator (2 static anycast IPs). Exam trigger: "clients' firewalls only allow whitelisted IPs" / "static IP for load balancer" → Elastic IP on NLB. Wrong answers: EIP on ALB (impossible), CloudFront (IP ranges change, can't target private IPs), anything about EBS volumes giving IPs (nonsense). See [[Elastic IP (EIP)]].

**VPC Endpoint Policy** — IAM-style resource policy attached to a VPC endpoint (Gateway endpoint for S3/DynamoDB, or Interface endpoint) that controls WHAT can be accessed THROUGH that endpoint. Default = full access. Restrict e.g. to specific S3 bucket ARNs → instances in the VPC can only reach trusted buckets via the endpoint. Doesn't replace IAM or bucket policies — all must allow (intersection). Other direction: bucket policy with `aws:SourceVpce` / `aws:SourceVpc` condition = bucket only accepts traffic from that endpoint/VPC. Exam trigger: "allow access only to trusted S3 buckets via gateway endpoint, avoid broad policies" → endpoint policy listing trusted buckets (one policy vs editing every bucket policy). "Bucket must only be reachable from our VPC" → bucket policy with `aws:SourceVpce` condition. See [[VPC Endpoints vs NAT Gateway]].

**IPv6-only Subnet (dual-stack VPC)** — every VPC must keep an IPv4 CIDR (IPv4 can't be disabled or removed at VPC level, no IPv6-only VPC). But you can add an IPv6 CIDR (/56 from AWS) → VPC becomes dual-stack, and then create subnets that are dual-stack OR IPv6-only (/64, no IPv4 at all). IPv6 addresses are all public/globally unique; for private-subnet outbound-only IPv6 internet use Egress-Only Internet Gateway (IPv6 version of NAT). Exam trigger: "IPv4 addresses exhausted, VPC already has IPv6, need future scalability" → create IPv6-only subnet and launch there. Wrong answers: bigger IPv4 subnet (temporary fix, same problem later), disable IPv4 / remove IPv4 CIDRs (not possible).

**RDS Multi-AZ Failover — CNAME Flip** — RDS Multi-AZ keeps a synchronous standby in another AZ. Primary fails (or AZ outage, instance type change, patching) → RDS automatically promotes standby and FLIPS the DB endpoint's DNS CNAME record to point at it, typically 60–120 seconds. App keeps using same endpoint name, reconnects. IP can't move because IPs belong to subnets and subnets can't span AZs. Standby serves NO reads (classic Multi-AZ instance); for reads use read replicas or Multi-AZ DB cluster (2 readable standbys). Exam trigger: "what happens when Multi-AZ primary fails" → CNAME switched to standby. Wrong answers: IP moved to standby, primary reboots, new instance created in standby AZ. Why app must connect via endpoint DNS name, never a hardcoded IP.

**AWS Global Accelerator — static anycast IPs** — Gives your app TWO static anycast IPs that front ALBs, NLBs, EC2 instances or Elastic IPs in ONE OR MANY Regions. Traffic enters the nearest AWS edge and rides the AWS backbone to the closest healthy endpoint; failover is automatic and needs no DNS change or client cache expiry. Endpoint weights = blue/green traffic shifting. Exam trigger: "too many ALBs/IPs across Regions, firewall allow-list, simplify" → Global Accelerator (NOT an NLB with EIP, which only solves one Region, and ALBs can't take an EIP). Single-Region static IP → [[NLB — Static IP / Elastic IP for Whitelisting]]. Contrast CloudFront: caches content at edge, Global Accelerator doesn't cache, it just accelerates TCP/UDP and gives static IPs.

**NAT Gateway — lives in the PUBLIC subnet (vs IGW doing NAT)** — NAT gateway is created IN A PUBLIC SUBNET (needs a route to the IGW + an Elastic IP). Private subnets point their route table `0.0.0.0/0` at it. One per AZ for AZ-independent resilience; each AZ's private route table uses its own AZ's NAT gateway. NAT gateway = managed (NAT instance = self-managed EC2). Egress-only internet gateway = IPv6 outbound only. The Internet Gateway itself does 1:1 NAT between an instance's private IP and its public IPv4 — so an instance with a public IP in a public subnet doesn't need a NAT device. A private subnet can't use the IGW directly. Exam trigger: "private subnet needs internet for patches, IPv4, fully managed" → NAT gateway in the public subnet. Traps: NAT in the private subnet, IGW in the private subnet, egress-only IGW for IPv4.

**AWS CloudFormation StackSets** — Deploy ONE CloudFormation template to MANY accounts and MANY Regions in a single operation, from the Organizations management account or a delegated administrator. Enforces consistent resources (specific EC2 instance types, IAM roles for Lambda, baseline config) across departments. A plain stack = one account + one Region. A template is just the blueprint. [[AWS Control Tower vs Organizations vs RAM]]: RAM SHARES existing resources, it does NOT deploy templates. Exam trigger: "consistent provisioning across accounts and Regions with pre-defined configuration" → StackSets.

**SNI — multiple SSL certificates on one ALB listener** — Server Name Indication: bind MULTIPLE TLS certificates to the same HTTPS listener on an ALB (or CloudFront, NLB TLS listener); the load balancer picks the right cert per hostname the client asks for. Exam trigger: "one load balancer, several different domains (checkout.mycorp.com, www.mycorp.com, yourcorp.com), all HTTPS, minimal configuration" → certificates + SNI. Wrong answers: wildcard certificate (only covers subdomains of ONE domain), HTTP→HTTPS redirect (forces HTTPS, supplies no cert), changing the SSL security policy (TLS versions/ciphers only). Classic Load Balancer does NOT support SNI.

**AWS SCT vs DMS Basic Schema Copy** — Heterogeneous migration (e.g. Oracle/SQL Server → Aurora/PostgreSQL) is TWO steps: AWS Schema Conversion Tool (SCT) converts schema + code first (secondary indexes, foreign keys, stored procedures, views), then AWS DMS moves the data (full load + CDC). DMS Basic Schema Copy only creates tables + primary keys, NOT secondary indexes, FKs or stored procedures — fine for tests or homogeneous moves. Exam trigger: "commercial licensed DB → open source, keep indexes/FKs/stored procedures" → SCT + DMS. Wrong answers: Glue (ETL), Snowball (bulk files), Basic Schema Copy alone. See [[DMS vs DataSync]].

**EC2 Tenancy — dedicated wins (launch template vs VPC)** — EC2 tenancy options: shared (default), Dedicated Instance (single-tenant hardware), Dedicated Host (whole server, BYOL/compliance, needs a host resource group). The VPC also has a tenancy attribute. If EITHER the launch template tenancy OR the VPC tenancy is dedicated, the instance launches DEDICATED. A VPC set to dedicated forces all launches dedicated; a template can request dedicated even in a default VPC; a template set to shared can't override a dedicated VPC. Exam trap: "LT1 dedicated + default VPC, LT2 default + dedicated VPC" → BOTH dedicated.

**DynamoDB Deletion Protection vs PITR** — Deletion protection = a table setting that blocks `DeleteTable` until you turn it off — PREVENTS accidental table deletion, zero maintenance. Point-in-Time Recovery (PITR) = continuous backups, restore to any second in the last 35 days into a NEW table — RECOVERS after the fact (still downtime + manual restore), doesn't prevent anything. On-demand backups / export to S3 = manual or scheduled snapshots. Exam trigger: "prevent human error from deleting the production table, least operational overhead" → deletion protection. "Recover from accidental write/delete" → PITR.

**DynamoDB capacity modes — on-demand vs provisioned + auto scaling** — On-demand: no capacity planning, pay per request, instantly absorbs spikes, scales to zero cost when idle. Provisioned: you set RCUs/WCUs; auto scaling adjusts them via CloudWatch alarms with a DELAY, so very sudden spikes can throttle. Provisioned fits predictable or gradually ramping traffic (cheaper at steady load, can use reserved capacity). Exam trigger: "unpredictable traffic, spikes happen very quickly, idle at night" → on-demand. "Predictable / steady baseline, control cost" → provisioned + auto scaling. Global tables and GSIs don't change the capacity-mode answer. Item size limit 400 KB.

**Aurora I/O-Optimized vs Aurora Standard** — Aurora storage configurations: Aurora Standard = pay per storage + per I/O request. Aurora I/O-Optimized = flat storage price, NO per-I/O charges, higher throughput/lower latency, up to ~40% cheaper when I/O is more than ~25% of your Aurora bill. Aurora storage is a shared distributed volume that auto-scales to 128 TiB — you do NOT pick gp2/gp3/io1/magnetic for it. Exam trigger: "Aurora, I/O-intensive/spiky, predictable cost, no manual tuning" → Aurora I/O-Optimized. Wrong answers: gp2, io1 provisioned IOPS, magnetic (not Aurora storage choices). Related: Aurora replicas share the same volume → replica lag in tens of ms (vs seconds for RDS MySQL read replicas); "replica lag" → Aurora.

**Cost Optimization Hub vs Compute Optimizer vs Trusted Advisor** — Cost Optimization Hub: one dashboard consolidating cost recommendations across accounts and Regions — rightsizing, idle resource deletion, Savings Plans and Reserved Instance purchases. AWS Compute Optimizer: ML on utilization metrics → recommends optimal INSTANCE TYPES/sizes (EC2, ASG, EBS, Lambda); does NOT recommend purchase options. Trusted Advisor: checks incl. idle RDS, underused EC2, expiring RIs (does NOT auto-renew RIs). S3 Storage Class Analysis: recommends Standard → Standard-IA only (not Glacier). Exam trigger: "costs too high, find idle/low-utilization EC2 + right size" → Cost Optimization Hub + Compute Optimizer. See [[Cost Allocation Tags]] for per-department billing.

**CloudFront — origin groups, field-level encryption, geo restriction, price class** — Multiple origins: one distribution can route by path pattern/content type to different origins (S3 for static, ALB for dynamic). Origin group: primary + secondary origin; CloudFront fails over automatically on errors/chosen HTTP status codes → HIGH AVAILABILITY. Field-level encryption: encrypt up to 10 specific POST fields at the edge with a public key, stay encrypted through the whole stack, only the app with the private key decrypts. There is no "KMS encryption in CloudFront". Geo restriction: allow/block countries — NOT for HA. Price class: which edge regions you pay for (cost), NOT routing. Signed URLs/cookies: restrict who can access: [[CloudFront Signed URLs vs Signed Cookies]]. Lock S3 to CloudFront with [[OAC (Origin Access Control)]]; filter IPs with WAF attached to the distribution (not S3, not SG/NACL).

**KMS key rotation — customer managed key vs SSE-S3 vs imported key material** — SSE-S3: S3 manages everything; EACH object gets its own unique data key (encrypted by a rotating root key) — easiest, but rotation is not configurable or auditable by you. SSE-KMS with a customer managed key (CMK): enable AUTOMATIC rotation (default every 365 days, configurable period), set as the bucket's default encryption, audit usage in CloudTrail. KMS key with IMPORTED key material: NO automatic rotation (you rotate manually). CloudHSM: you manage keys/hardware — highest ops. Encryption context = extra authenticated data, does not generate keys. Exam trigger: "rotate keys every 12 months, auditable, least overhead" → SSE-KMS CMK with automatic rotation. "Each object different key, no extra work" → SSE-S3.

**S3 one-time cross-Region copy — Batch Replication vs aws s3 sync** — Live replication (CRR) only copies NEW objects after it's enabled. To copy EXISTING objects once: S3 Batch Replication (Batch Operations job; works for existing, previously failed, and previously replicated objects — delete the replication config afterwards), or `aws s3 sync s3://src s3://dst` (CopyObject between buckets, re-runnable without duplicates, only current versions). Console copy/paste doesn't scale to petabytes. S3 Transfer Acceleration speeds client↔bucket over distance, NOT bucket-to-bucket. Snowball is for on-prem/edge → AWS, not Region-to-Region. Exam trigger: "one-time copy of 1 PB between Regions, Snowball not allowed" → Batch Replication + `aws s3 sync`.

**Fargate — serverless containers (ECS vs EKS, launch types)** — AWS Fargate = serverless compute for containers: no EC2 instances to patch or scale. Works under BOTH Amazon ECS and Amazon EKS. ECS/EKS with the EC2 launch type = you manage the instances (NOT serverless). ECS service auto scaling (target tracking) scales task COUNT on the ECS SERVICE's metrics (CPUUtilization / MemoryUtilization in the ECS namespace); ALB and target groups have no CPU metric; an alarm is the trigger, not a metric source. Lambda vs Fargate for a small Python microservice, minimal ops: Lambda + API Gateway (Fargate needs a Dockerfile/image). EMR and SageMaker aren't container orchestrators. Exam trigger: "serverless orchestration of Docker containers" → ECS + Fargate and/or EKS + Fargate.

**EventBridge vs SNS vs SQS — decoupling with SaaS/third parties** — EventBridge: event bus with rule-based routing on event content, ingests events from 90+ AWS services AND native third-party SaaS partners, many targets (Lambda, SQS, SNS, Kinesis, ...). SNS: pub/sub fan-out push to subscribers, no native SaaS-partner integration. SQS: pull-based queue between YOUR producers and consumers. ELB: synchronous, NOT decoupling. Exam trigger: "SaaS application feeds updates to in-house and third-party apps, asynchronously decouple" → EventBridge. "Buffer work between my own services" → SQS. "Same message to many subscribers" → SNS.

**ElastiCache for Redis — geospatial (GEO) commands** — Redis natively stores/queries latitude-longitude: `GEOADD` (store a point), `GEORADIUS`/`GEOSEARCH` (everything within a radius, e.g. nearest drivers), `GEODIST` (distance). In-memory, sub-millisecond, handles thousands of reads+writes per second; use TTLs so stale locations expire. Exam trigger: "real-time location tracking, nearby drivers, RDS PostgreSQL bottleneck on frequent reads/writes" → ElastiCache for Redis in front. Wrong answers: RDS Multi-AZ standby (failover only, can't serve reads), read replica auto scaling (doesn't fix write load, adds lag), OpenSearch (search/analytics, poor at high-frequency updates). See [[ElastiCache — Redis vs Memcached]].

**DMS — non-database uses (S3 source → Kinesis target)** — AWS DMS isn't limited to database-to-database: S3 can be a SOURCE and Kinesis Data Streams / MSK a TARGET. It handles full load AND change data capture (CDC) of ongoing file updates with no custom code, scaling via the replication instance. Exam trigger: "stream existing S3 files PLUS ongoing updates into Kinesis Data Streams, fastest to build" → DMS (S3 source, Kinesis target). Wrong answers: S3 event notification + Lambda (custom code, only sees NEW events, not the existing files), EventBridge + Lambda (needs CloudTrail data events + custom code), "S3 → SNS → Kinesis" (S3 can't write straight to SNS-as-bridge and SNS can't publish to Kinesis Data Streams). See [[DMS vs DataSync]].

**Aurora endpoints — cluster vs reader vs custom vs instance** — Aurora hides instance hostnames behind endpoints. Cluster (writer) endpoint: always points to the current PRIMARY, use for writes/DDL and it follows failover. Reader endpoint: one per cluster, load-balances connections across ALL Aurora Replicas (read-only); with zero replicas it points to the primary. Custom endpoint: you pick a subset of instances (e.g. big instances for reporting). Instance endpoint: one specific instance, for diagnosis/tuning. Exam trigger: "balance read traffic equally across the replicas" → reader endpoint. Wrong answers: Network Load Balancer in front of replicas, cluster endpoint (writer), Parallel Query (pushes ONE query's compute into the storage layer, no read balancing). See [[RDS vs Aurora]].

**CloudFormation CreationPolicy + cfn-signal (vs DependsOn / UpdatePolicy / UpdateReplacePolicy)** — CreationPolicy on a resource (EC2 Instance, Auto Scaling group, WaitCondition) holds it in CREATE_IN_PROGRESS until CloudFormation receives N success signals or the timeout hits. The instance sends the signal with the `cfn-signal` helper script (or the SignalResource API) after the software is installed. `cfn-init` only CONFIGURES the instance (reads metadata, installs packages), it does not signal. DependsOn only orders resource creation, it does not wait for software. UpdatePolicy = how an ASG/Lambda alias is updated during a stack update. UpdateReplacePolicy = retain or snapshot the old physical resource when it is replaced. Exam trigger: "make sure the applications are running before stack creation proceeds" → CreationPolicy + cfn-signal.

**Glacier provisioned retrieval capacity (Expedited guarantee)** — Glacier Flexible Retrieval Expedited retrievals (1-5 min) are normally best-effort and can be rejected in rare high-demand periods. Provisioned capacity guarantees Expedited availability: each unit gives at least 3 Expedited retrievals every 5 minutes and up to 150 MB/s of retrieval throughput. Applies to Expedited ONLY (not Standard 3-5 h, not Bulk 5-12 h). Ranged retrieval (a portion of the archive) saves cost/time but adds no capacity. Exam trigger: "surprise audit, must be retrievable in under 15 minutes under ALL circumstances, up to 150 MB/s" → Expedited retrieval + purchase provisioned capacity. See [[Glacier Flexible Retrieval tiers (Expedited/Standard/Bulk)]].

**Reserved Instance Marketplace + EC2 billing by state** — Reserved Instances bill for the whole term whether the instance runs or not, and even AFTER the instance is terminated. To stop paying early: sell unused STANDARD RIs on the Reserved Instance Marketplace (selling on Amazon.com or "cancelling an AWS subscription" are not options). Terminate the decommissioned instances too, because when an RI expires covered instances revert to on-demand pricing, and a stopped instance can be restarted. EC2 billing by state: pending = not billed; running = billed; stopping (to stop) = not billed; stopping (to HIBERNATE) = billed; stopped = no instance charge (EBS and Elastic IP still bill); terminated = not billed (RI term still is). Exam trigger: "app decommissioned, stop paying for Reserved instances" → RI Marketplace + terminate.

**SSM Parameter Store SecureString vs Secrets Manager** — Parameter Store (Systems Manager): hierarchical config store; plain String/StringList or SecureString encrypted with KMS; standard parameters are FREE. Good for DB hostnames, environment settings, license/product keys and passwords that do not need rotation. Secrets Manager: charged per secret per month plus API calls; adds AUTOMATIC ROTATION (native for RDS/Aurora credentials via Lambda), cross-Region secret replication, fine-grained resource policies. Exam trigger: "store app variables/passwords encrypted, MOST cost-effective" → Parameter Store SecureString + KMS. "Automatically rotate DB credentials" → Secrets Manager. Wrong answers: S3 file (manual updates), SSM OpsCenter (ops items, not a key-value store).

**RDS / Aurora backup retention limits → AWS Backup** — RDS and Aurora automated backups keep at most 35 DAYS (0-35, retention 0 disables them). Longer retention (e.g. 90 days, compliance) → AWS Backup plan with a schedule and retention you choose (also cross-Region/cross-account copy and Vault Lock), or manual snapshots (kept until you delete them). Automated snapshots cannot be exported to S3 automatically: export is manual, and you copy the automated snapshot to a manual one first. Exam trigger: "90-day (>35-day) retention for Aurora/RDS" → AWS Backup. Wrong answers: raise automated retention to 90, auto-export snapshot to S3 + lifecycle, Lambda that downloads snapshots. See [[Amazon Data Lifecycle Manager (DLM) vs AWS Backup]].

**EC2 service quotas — vCPU limit is per Region** — EC2 On-Demand limits are measured in vCPUs per Region (by instance family group), not as a flat count of instances and not per Availability Zone. Reserved Instances: 20 per Region by default; Spot has its own limit. New accounts may start lower. Exam trigger: "script requests 50 instances in one AZ, the first 20 succeed, the rest fail" → hit the vCPU-based On-Demand quota; request an increase in Service Quotas / the limit form and retry. Wrong answers: switching AZ or Region (the limit applies per Region and can be raised), "the EC2 API had an issue".
